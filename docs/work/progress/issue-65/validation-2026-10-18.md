## 修复与机器守卫

1. **后台服务生命周期**：`getRuntime()` 在测试模式也启动 Durable worker，提前消费没有执行渠道的测试计划并阻止进程退出。启动与后台补投现遵守 `liveServicesDisabled()`。公共计划 API 原有排队断言修复前失败；新增断言直接检查两个启动方法未被调用，去除守卫的故障注入也会失败。
2. **恢复审批所有者**：原生 Room 卡片走 Room HTTP 入口，该入口把重启后的持久化审核误当成已失效的内存 runner。共享 resolver 现只允许非活跃执行处理身份匹配的 `recovery_review` 请求；仍校验 Agent、成员资格、上下文、run 与当前权限。普通非活跃工具审批拒绝。旧测试直接调用 Desktop Broker，漏掉真实 Room 入口；已改成 Room HTTP 入口，修复前批准与拒绝两例均返回 400。
3. **重复重启的恢复筛选**：`piRecoveryCandidates` 保留审核记录却不返回它，Room 启动清理因而中断仍在审核的执行。现将 `recovery_review` 纳入启动保护。新增筛选测试修复前失败；集成测试在首次进入审核后再杀进程，重启后校验同一审批、批准前零重发，以及批准/拒绝各自的最终状态。

前两类问题已在 CLAUDE pitfalls 补充长期守卫要求。第三类归入持久化状态与恢复所有权问题，以候选筛选与两次重启回归锁定，不另加重复规则。
