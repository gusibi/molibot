## Problem Statement

用户希望 Molibot 能可靠推进长任务、组合工具处理复杂工作，并直接使用可选的图片模型。当前 Pi 已升级到 1.0，但这些新能力尚未完整接入产品。

Molibot 已有 Durable Execution、计划、审批、任务预算、跨渠道入口和媒体任务。继续并行维护另一套工具和执行系统，会使权限、取消、恢复和费用归属出现两套真相。仅保存计划或执行状态，也不能保证工具调用级断点恢复；已有步骤恢复存在最后一个安全 intent 掩盖前面未知副作用的缺口。

本需求涉及四项明确能力：Codemode、Pi 图片生成、Pi Durable、Deferred provider response。它们需要完整接入现有产品入口，而不是增加未被调用的 SDK 方法。

## Solution

用 Pi Durable 替换底层模型/工具执行内核，保留 Molibot 目标、计划、审批、验收、预算、渠道和定时产品语义。Deferred provider response 与同一执行内核共同设计，在支持的 Provider 上持久等待异步模型任务。Codemode 通过现有共享工具执行边界组合工具。Pi 图片生成成为现有媒体生成体系的可选后端。

分四阶段交付；第四阶段包含两个可独立验收的模块：

| 阶段 | 交付范围 | 前置条件 | 可观察完成标准 |
| --- | --- | --- | --- |
| 1 | Pi Durable 最小端到端闭环 | 固定上游版本、确认存储与权限适配方式 | 从现有入口创建任务、执行、真实进程中断、同库重启续跑、验收；已提交工具不重复执行 |
| 2 | Durable 正式覆盖现有执行入口 | 阶段 1 的恢复和审批契约验证通过 | 普通对话、计划、长任务、自动化和内部子 Agent 接入同一内核；现有产品能力无回退；删除被替代的执行机制 |
| 3 | Deferred provider response | 阶段 1 预留等待状态；阶段 2 稳定执行映射 | 异步 handle 已提交后重启继续轮询，结果只入账一次，不重新提交同一远端任务 |
| 4A | Codemode | 阶段 2 的工具、取消、审批桥接稳定 | 同一授权边界内组合调用、筛选结果；每个内部调用可审计，不绕过审批 |
| 4B | Pi 图片生成 | 现有媒体入口与制品契约；无需等待 Codemode | 可选图片模型真实生成并落制品、预览与发送；既有图片后端继续可用 |

默认按表中顺序实施。4B 与 Durable 内核低耦合，若分配独立 agent，可提前并行，但不得与其他 agent 争用同一工具注册/设置修改；Codemode 不得成为图片生成必需入口。阶段 1 和 2 属于同一个内核替换项目，不能把试验路径长期保留为第二套生产引擎。

## User Stories

1. 作为用户，我希望长任务中断后能继续执行，以便不用重新描述目标。
2. 作为用户，我希望已完成的工具操作不会因重启再次执行，以便避免重复工作。
3. 作为用户，我希望未知是否成功的外部操作明确请求确认，以便避免重复发送或重复扣费。
4. 作为用户，我希望任务继续使用原来的计划和验收标准，以便更换底层引擎不会改变目标。
5. 作为用户，我希望审批挂起后重启仍显示同一个待审批操作，以便不用重新授权。
6. 作为用户，我希望批准或拒绝只生效一次，以便多次点击不会启动重复执行。
7. 作为用户，我希望停止操作触达正在执行的工具和子 Agent，以便控制运行成本和外部操作。
8. 作为用户，我希望停止后不会出现迟到结果把任务改成成功，以便状态值得信任。
9. 作为用户，我希望已经发生的外部操作在停止后仍可查看，以便知道停止实际阻止了什么。
10. 作为用户，我希望预算跨重启和子任务累计，以便费用不会因恢复被重置。
11. 作为用户，我希望在现有渠道与 Desktop/Web 中看到相同任务进度，以便不必学习新入口。
12. 作为用户，我希望会话断线重连后恢复当前状态，以便不会看到重复消息或过期进度。
13. 作为用户，我希望计划的批准、修订和继续操作保留现有语义，以便任务不会执行未经批准的内容。
14. 作为用户，我希望模型说“完成”后仍经过任务验收，以便工具成功不被误认作目标完成。
15. 作为用户，我希望提醒和周期自动化继续使用现有 Runtime Task，以便执行引擎替换不改变定时管理方式。
16. 作为用户，我希望子 Agent 在进程重启后恢复原有身份和工作，以便避免重复委派。
17. 作为用户，我希望 Agent Room 的参与者保持独立 Agent Context，以便底层任务关系不改变房间含义。
18. 作为用户，我希望跨 owner、Project 和会话的恢复严格校验权限，以便我的数据不会被别的任务读取。
19. 作为用户，我希望支持异步响应的模型能在后台继续处理，以便等待期间不用维持浏览器连接。
20. 作为用户，我希望异步模型任务重启后继续查原任务，以便不重复提交和计费。
21. 作为用户，我希望异步任务失败、过期或状态未知有清楚说明，以便决定是否重试。
22. 作为用户，我希望取消异步模型任务时知道远端是否实际取消，以便不误以为费用已经停止。
23. 作为用户，我希望普通同步模型继续正常使用，以便 Provider 不支持异步响应也能完成任务。
24. 作为用户，我希望助理用脚本组合批量查询和数据整理，以便减少多轮工具调用。
25. 作为用户，我希望 Codemode 对每个内部工具调用遵循现有权限，以便脚本不能绕过审批。
26. 作为用户，我希望脚本失败时保留已成功操作的回执，以便不把部分成功当成全部失败并盲目重试。
27. 作为用户，我希望大型工具结果先筛选再交给模型，以便减少上下文占用；费用改善以测量为准。
28. 作为用户，我希望脚本无限循环、超时或无响应不会拖垮 Molibot，以便其他会话继续可用。
29. 作为用户，我希望 Codemode 不暴露我无权使用的工具或凭据，以便工具发现也遵守权限。
30. 作为用户，我希望从现有图片设置选择可用的 Pi 图片模型，以便使用已有 Provider 凭据。
31. 作为用户，我希望生成的图片成为真实可下载、预览和发送的制品，以便结果可以使用。
32. 作为用户，我希望图片编辑只在模型支持时提供，以便不会向不支持的模型发起请求。
33. 作为用户，我希望图片失败、取消、超时与费用显示准确，以便不会看到虚假的成功结果。
34. 作为用户，我希望更换图片模型不删除既有图片后端配置，以便其他已支持的生成方式继续可用。
35. 作为用户，我希望配置重启后保留，界面支持中英、明暗主题和窄屏，以便新增能力和现有产品体验一致。
36. 作为维护者，我希望按阶段拿到可运行代码、验证证据和明确限制，以便独立 agent 能接力实现。
37. 作为维护者，我希望历史会话和用户文件不被切换引擎静默覆盖，以便保留用户已有数据。

## Implementation Decisions

### 共同架构约束

- Pi 管理底层 generation/tool task checkpoint、已提交执行结果和任务所有权；Molibot 管理 Durable Execution、Execution Step、Acceptance Criterion、Decision Request、Task Budget 和来源授权。二者使用稳定身份映射，不共同写同一个状态机。
- UI Session 与 Agent Context 分离；Pi conversation 不是新的用户任务列表，也不直接等同于 Agent Room。每个 Room Participant 的 Agent Context 和现有发言/写入协调语义必须保留。
- Runtime Task 仍是 watched event JSON 的用户 CRUD 聚合，Runtime Event 仍负责触发；Pi 内部 scheduler 只处理执行任务，不替换提醒和周期调度。
- 工具执行统一经过共享授权、审批、副作用分类、执行槽位、截止时间和 receipt 边界。Pi 默认工具、Codemode 和 models 全局接口不得提供绕行入口。
- 开始执行时绑定 owner、Agent、Project、UI Session、权限、模型与策略快照。恢复不提升权限；撤销授权后需按现有安全规则阻止未执行动作。参数或目标变化不得复用旧审批。
- 业务域按已有 ADR 分库，Pi 内部状态按其正式 SQLite 接口保存；需要原子提交的底层 transcript/task/result 留在 Pi 自己的提交边界。跨库投影通过稳定事件身份幂等更新，启动时 reconciliation。不得宣称跨库事务，不得把底层 task 状态再复制成第二套可写状态机。
- 阶段 1 必须确认 Pi 内部 document 表示与现有 ADR 的适用边界；若必须改变已接受的架构约束，先提交精确 ADR 修订并由负责人决定，不偷偷放宽规则。
- 每个存储实例只有一个活动进程 owner；第二个实例不得同时打开执行存储。没有分布式锁的情况下不得提供多进程调度保证。
- 保留临时工具控制、面向用户的说明和结构化运行事件的分离；不能把“本轮不要调工具”等控制消息保存为普通对话。
- 最终渲染后的真实系统提示词继续正确合并 Bot/profile/skill，并保持动态工具发现和缓存稳定前缀；不能只验证 preview。
- 优先采用 Pi 现成正式能力与现有成熟依赖。固定经过验证的版本，避免实验 API 漂移；不要另写通用 Harness、通用工作流 DAG 或新配置框架。

### 阶段 1：最小可靠执行闭环

**实现责任：** 共享 Agent 执行适配、Pi 存储生命周期、现有工具桥接、临时服务恢复验收。不扩展设置页和房间功能。

1. 从现有共享任务入口推进一个已批准的 Durable Execution，映射一个 Execution Attempt 到 Pi 底层执行，不引入第二个产品入口。
2. 工具最终参数及执行 intent 必须先提交；结果与底层任务完成按 Pi 提供的原子边界提交。保留可关联的 Molibot Side-effect Record 和 Evidence。
3. 验证生成报告、外部发送模拟器、更新记录的完整链路。已提交工具结果必须复用；未知成功的非幂等调用不得自动重放。
4. 解决当前仅看最后一个 intent 的恢复缺口，必须对所有相关操作逐个核对完成结果和未知副作用。修正在最终共享恢复路径完成，不能只给某个 Channel 加特判，也不先加临时补丁再延期根修。
5. replay safe 必须是工具契约而不是模型声明；相同参数 hash 不是外部幂等保证。queryable 工具须真实注册查询逻辑；没有查询器或结果 unknown 时创建 Decision Request。
6. 审批挂起、同库重启和一次性回答应在本阶段跑通，不允许先用“审批永远通过”的示例替代。
7. Pi 的 unsafe interrupted 错误不能仅交给模型自行判断后新发相同危险调用；Molibot 须记录未决操作并阻断其未经核对的再次执行。
8. 本阶段不是生产切换，也不并行运行两套引擎处理同一任务。试验入口必须隔离；进入阶段 2 前移除一次性试验装配。

**验收门槛：** 正常完成、已提交结果后强杀恢复、外部成功但本地未提交、前危险后安全两个 intent、审批等待重启、重复恢复、取消与迟到结果全部通过。外部模拟器的操作次数独立于 Molibot 数据库记录检查。用受控 barrier 在真实执行窗口终止子进程，不能只注入 running 行。

**停止条件：** 上游无法满足权限、审批或副作用阻断，或需要未经批准的 ADR/数据破坏性变更时，停止依赖部分并记录明确差距；不默默回退到另一套长期引擎。

### 阶段 2：正式内核替换与产品能力保留

**实现责任：** 共用 runner/session continuation、计划与 Durable coordinator 对接、队列与流式投影、内部子 Agent 生命周期。相关产品 UI 只做必要适配。

1. 普通对话、Session 计划执行、Durable Execution attempt、自动化触发与内部子 Agent 统一进入 Pi 内核；是否创建 Durable Execution 仍由 Molibot 激活规则决定，不把普通聊天变成用户长任务。
2. 计划首次批准绑定内容版本，执行进度回写原有投影；验收仍由 Acceptance Criterion/证据/用户确认决定，不以 model stop 或 tool success 直接替代。
3. 定义唯一恢复负责人：入站队列只负责一次逻辑输入的交付，Pi 负责执行续跑，Molibot 负责目标级决策和续步触发。恢复时不得让旧队列重投与 Pi resume 各启动一份工作。
4. 审批请求、回答和底层 invocation 使用稳定关联 ID；重复点击、过期批准、跨 owner 批准不执行工具。任务终结清理 terminal 队列行与审批等待。
5. 取消与暂停明确区分。取消传播活动调用和前台子任务，屏蔽迟到提交；暂停阻止后续新动作，保留安全已完成结果。不能声称可撤销已发生的外部操作。
6. 保留 Task Budget 与现有 attempt/run 截止时间。恢复、子 Agent 和重复通知不重置额度；同一 usage receipt 不重复入账，缺失 Provider 费用明确为未知。
7. 前台子 Agent 持久保存身份、所有权与结果；恢复不重复创建。后台任务必须显式具有生命周期边界，并按现有授权规则处理父任务停止；不能从 Pi 默认行为推导用户已授权永久后台运行。
8. 用现有流式事件与制品/Trace 投影展示 Pi 的已提交状态；断线重连恢复快照，事件去重。保留 Turn Retention Policy、搜索/记忆边界和所有权，不新增旁路 transcript 回灌。
9. 切换前清点历史 Agent Context 和活动执行数据。保留历史只读展示；不建立旧格式执行 fallback、兼容层或自动 migration。不能安全直接续跑的旧活动任务需显式进入人工处理，不静默删除或伪造完成。需要转换或破坏性清理时提交负责人决策。
10. 通过验收后删除被替代的底层模型循环、工具回合重放、重复取消/恢复逻辑；保留 Molibot 业务 coordinator、权限、验证器和 Runtime Task 系统。

**验收门槛：** 阶段 1 场景全部在正式入口通过；普通对话、批准计划、事件触发、父子任务恢复、排队插入、跨 owner 拒绝、预算与取消、Agent Room 隔离均有行为证据。Desktop/Web 加至少两个不同 Channel adapter 的契约验证；真实外部 transport 与 Provider 验收没有执行时必须保留待验证标记。

### 阶段 3：Deferred provider response

**实现责任：** Provider 异步响应适配、持久 handle、同一逻辑请求的等待/取消/费用归属。不是 deferred tool discovery。

1. 阶段 1 设计请求身份和等待态时纳入 Deferred；本阶段只启用实际支持且已验证该协议的 Provider/model。
2. handle 和等待阶段提交后，重启继续查询原远端请求，不创建新远端任务。结果、usage 和终态按稳定请求身份只入账一次。
3. 提交远端任务成功但 handle 尚未落盘仍存在未知窗口：只有 Provider 提供有效幂等提交/按请求身份查询时才安全恢复，否则显示状态未知并要求决定，不盲目重发。
4. pending 保留，不占用长期本地工具调用栈；采用 SDK 支持的有界轮询和错误分类，遵守预算/总截止时间。不要自行另建 OS scheduler 或重复持久轮询系统。
5. 取消时分清本地停止等待、向远端申请取消和远端确认取消；远端不支持取消时明确提示费用可能继续。迟到响应不复活已取消任务。
6. 明确处理 transient error、远端失败、过期、丢失 handle、凭据失效与结果未知。过期或失效不自动切同步模型再付费。
7. 不支持 Deferred 的 Provider 从请求开始就使用普通同步路径；这是不同能力的正常分派，不是失败后的隐式 fallback。同步流式请求中断可能重发，不能承诺无重复计算费用。

**验收门槛：** 支持/不支持 Provider 分派、pending 后重启、重复轮询/重复结果、提交未知窗口、失效 handle、取消及迟到结果、usage 去重。使用 fake provider 验证协议，再按可用凭据记录真实 Provider 验收；不凭 fixture 宣称某个服务商已支持。

### 阶段 4A：Codemode

**实现责任：** Pi 脚本运行能力适配、受控工具 bridge、工具发现与 Trace；不替换 MCP 管理。

1. 复用 Pi 的脚本引擎，在其正式可适配接口上接入 Molibot；先确认导出入口和生命周期，不复制内部源码或为接入伪造第二套 Pi Session。
2. 脚本只能通过受控 bridge 调用当前任务有权访问的工具。ALL_TOOLS/search/describe 等发现接口同样按权限过滤；每次实际调用重新走正式授权边界。
3. 每个内部调用使用独立稳定 invocation 身份，记录参数、intent、receipt、预算与 Trace；Codemode 本身不是绕过危险操作判定的“大工具”。
4. 先验收组合只读查询和结果过滤，再在同一模块内补齐有副作用工具的审批/恢复。独立只读调用可并行，写操作继续遵守共享执行槽位和既有协调规则。
5. 审批挂起后不能把整段含副作用脚本盲目重放。需证明底层调用结果复用和脚本续接协议安全；无法续接时保留已完成回执并要求重新规划剩余部分。不能把任意 JS 脚本标记 replay safe。
6. 运行环境不给脚本直接 Node、文件系统、网络或宿主凭据访问。遵守既有不可信运行时进程边界，验证无限循环、内存上限、截止时间和取消不会阻塞主服务；VM 权限边界不能替代故障隔离证据。
7. 限制模型可见输出，大内容走制品安全引用；脚本失败保留部分结果，明确此前真实操作不会自动回滚。脚本退出后不留下未等待的工具运行。
8. 初版保留直接工具调用，与 Codemode 共用同一底层 dispatcher；不强制所有模型只用脚本。
9. 不直接开放未经 Molibot 管理的 models 调用。若暴露现有分类或新图片模型，必须通过同样的凭据、预算、审计与媒体任务 bridge，不能新增费用旁路。

**验收门槛：** 批量查询筛选、受限工具发现、审批拒绝/挂起恢复、成功副作用后脚本失败、无限循环隔离、停止后无残留工作、输出截断和制品可读、嵌套 Codemode 拒绝、无直接网络/文件/凭据访问。用同一任务测量请求次数与输入量，未经测量不宣称一定降低成本。

### 阶段 4B：Pi 图片生成

**实现责任：** 现有图片 Provider adapter、operation-specific 模型发现与设置、媒体任务/制品/渠道展示。保持现有图片入口。

1. 在现有图片生成 Provider 契约中调用 Pi Models.generateImages，不新增另一套图片任务库。依据已验证的图片模型能力筛选，不把 chat/classifier 列表混为图片列表。
2. 复用现有 Provider 身份和 CredentialStore；图片任务绑定所选 Provider/model，不因恢复或设置变化悄悄更换模型。缺少凭据时明确提示配置。
3. 支持文本生成，图片编辑/参考图只对支持的模型开放。参数按实际能力适配， unsupported 参数不假装生效。
4. Pi 多个图片输出与伴随文本不能静默只保留第一张；按现有任务与制品机制注册全部成功输出，记录顺序、MIME 和安全引用。大图或 base64 不进入普通文本、日志和长期静态提示词。
5. 图片落到现有制品生命周期，Desktop/Web 可预览下载，Channel 只做发送适配。服务重启后已落盘图片可访问；部分保存失败时明确区分生成成功与制品保存失败。
6. 正确处理 SDK 的 stop/error/aborted 结果与可能缺失的 usage；无图片输出不能伪造成功。不因超时自动换 Provider 发起另一笔付费请求。
7. 图片任务和 Codemode 调用共享预算/费用归属，同一图片请求不能双计。对生成成功但结果未知的中断按副作用规则处理，不盲目重试。
8. 设置走该实体细粒度保存和整对象 round-trip 测试；保留既有图片后端配置。UI 遵守现有设计、组件和固定保存底栏，验证中英、主题、移动宽度及语言即时切换。

**验收门槛：** 有/无凭据、能力筛选、文本生图、支持模型参考图、多图加文本输出、取消/错误/空输出、usage 缺失、保存后重启、制品下载、至少一个 Channel 的图片发送契约。真实付费生成只有在测试凭据和费用授权具备时执行，缺失则明确待验证。

## Testing Decisions

- 主要 seam：现有共享 Chat/任务入口与公开控制、状态查询入口，配合可重启的临时服务、临时数据库和本地 Provider/tool fixture。测试目标是用户看到的结果、外部操作次数与授权效果，不断言私有方法调用顺序或某张内部表结构。
- 图片沿用现有媒体任务/生成入口，复用同一临时服务 fixture；不另建通用测试框架。只有高层难以确定性复现的提交窗口和存储原子性才补充窄层测试。
- 参考现有 Durable store/runtime/approval 测试、冷启动恢复 eval、runner 真实请求测试、工具执行与取消测试、媒体生成/任务测试、settings 临时数据库 round-trip、Desktop chat 行为测试。
- 重启恢复测试必须在运行中的真实子进程操作窗口强杀，通过 barrier 和外部 fixture 独立 ledger 判断工具是否实际执行。单纯种植崩溃状态记录只能验证 reconciliation，不能验收执行恢复。
- 按阶段固定测试矩阵：正常路径、重复输入/按钮/事件、权限拒绝、重启、未知外部结果、取消、迟到结果、预算耗尽和证据失效。外部 fixture 的 ledger 独立于运行时数据库，避免测试与实现共享错误判断。
- 所有 SQLite、settings、队列、Trace 和审批测试隔离 DATA_DIR，不读取或写入用户运行数据，不中断用户服务。
- UI 变更需相关测试、Svelte 检查、build 和真实冷路径：首次打开、切换 UI Session/页面、服务中断恢复；同时检查中英、主题和窄屏。新增设置须 save → 新 store → load 整对象回归。
- 每个阶段交付时做对抗审查：检查更简单实现、层级泄漏、重复状态来源、错误的 safe replay、跨库丢事件、权限变更和取消竞态；修复本阶段引入的问题后交付。
- 必需检查失败先区分本阶段与既有问题；记录具体证据和未验证项，不以已有升级测试或 fixture 通过代替本阶段验收。
- 当前测试边界待负责人确认；确认只影响最终验收契约，不阻止本文生成。实现 agent 开始依赖该契约前应读取最新确认记录。

## Out of Scope

- 重做 Molibot 产品层、计划看板、Agent Room、MCP 管理、Channel transport、记忆或定时任务体系。
- 通用分布式工作流引擎、多主机/多进程共享同一 Pi 存储、外部操作 exactly-once 保证。
- 永久双执行引擎、向后兼容层、自动历史数据 migration、静默删除或覆盖用户状态。
- 任意 JS 程序的透明断点续跑、任意工具的无条件安全重放、停止后撤销已发生的外部操作。
- 全量采集原始 Provider 事件、敏感参数或未脱敏错误；扩大本需求无关的 telemetry。
- 全面图片编辑器、视频生成、强制替换所有图片后端、给所有 Provider 强加 Deferred。
- 未授权的付费测试、部署、版本发布；清理用户已有未提交修改。

## Further Notes

- 本 spec 明确将四项能力纳入分阶段实现范围，尚未交付。不得把计划状态写成已交付；每阶段实际能力改变时在同一 slice 更新能力矩阵与适用交付文档。
- 交接按阶段/模块划分责任。阶段 1/2 由同一执行内核负责人衔接；阶段 3 负责 Provider 等待；阶段 4A 负责脚本与工具 bridge；阶段 4B 负责图片 adapter 与媒体 UI。多个 agent 同时实施前明确共享注册、settings 和 runner 的唯一编辑负责人，不撤销他人改动。
- 每阶段交付包含运行入口、相关检查结果、真实验收证据、未验证项、删除的旧机制与下一阶段依赖。阶段结束不以“已添加接口”作为完成。
- 接受的 ADR：不可信代码故障隔离；Runtime Task 与 Mini App Todo 边界；按业务域分库及机器状态所有权。Pi 内部 typed document/task 的存储是需明确界定的接入边界，不能借采用库绕过现有规则。
- 既有长任务 PRD 保留目标级产品语义；其旧底层执行实现说明在本替换范围内由本文取代。计划看板 PRD 的独立未交付产品需求保持原有范围，不顺手纳入本项目。
- Pi Durable 仍为 Experimental；版本固定和适配验证是切换前置，不将 Pi 总版本 1.0 等同于 Durable API 稳定。
- Issue 发布需要项目 tracker/triage 配置；当前未提供。完成 `/setup-matt-pocock-skills` 后可将本文作为 issue 正文并应用 ready-for-agent。本文暂作本地交接，不声称已发布 issue。
