# Molibot Personal Agent：授权事项的持续跟进与交付 PRD

> 版本：v0.2 · 2026-10-18
>
> 状态：产品方案草案，待试用验证与实施评审。本次修订授权仅为完善方案，不代表批准开发或外部集成。
>
> 首个验证人群：已在 Molibot 中处理项目工作的独立开发者、个人创作者。
>
> 产品承诺：把一件具体的事交给 Momo 后，少重复背景、少查询进度，并获得有依据的下一步帮助。

实施契约见 [Phase One 实施 Spec](../designs/agent-runtime/personal-agent-follow-up-spec.md)，包含共享服务、存储、事件恢复、投递与验收切片；Phase Two/Three 保留扩展边界。

## 1. 定位与问题

Personal Agent 的价值是持续接住用户交代的事情，并减少用户为推进事情付出的管理成本。

当前系统已有记忆、定时任务、运行时事件、渠道通知和执行恢复基础。缺口是这些能力尚未形成面向已授权事项的持续服务：知道负责什么、从哪里获取进展、什么时候介入、能准备什么、如何确认结束。不能把现状描述成“只有用户消息才能触发”。

首版聚焦三个可观察的问题：

- 用户跨会话需要重复解释同一事项的背景和协作偏好。
- 用户需要自己反复查看计划、执行结果和产物，才能发现缺口或阻塞。
- 提醒只告诉用户“该做了”，没有减少准备材料、判断下一步的工作。

“用户愿意长期委托、节省的时间超过配置成本、愿意为此付费”均为待验证假设。先验证项目工作场景，不承诺覆盖所有人的工作与生活。

### 当前依据与文档边界

能力状态仅以 [能力矩阵](personal-assistant-capability-matrix.md) 为准，修订依据为其 2026-10-17 核验记录；复用基础不等于本方案已交付。

本文件原位替代 2026-10-14 的“主动助手 V1”草案，并整合产品升级 PRD v0.1；三阶段以本文件为规划依据。[身份与导航规格](personal-agent-experience-v1.md)继续独立有效；[项目自动任务](project-automations-prd.md)、[持久执行](automatic-durable-execution-prd.md)及[大型自治目标](large-autonomous-execution-prd.md)保留各自职责，本方案不把这些未完成能力视为现成依赖。

## 2. 首个完整场景

用户：“帮我跟进周五的方案交付，检查这个项目里关联的计划和指定草稿。发现缺口时告诉我，并准备下一步建议；周四晚上无论有没有进展，都和我核对一次。”

Momo 确认负责的事项、来源、完成标准、检查条件、结束时间和通知目标。创建成功后展示一张简短的委托摘要；范围明确的只读检查和建议准备在授权有效期内持续生效。

后续检查有证据发现预算部分仍为空时，Momo 可告知：“指定草稿截至今天 18:00 仍缺预算部分。我根据项目里已有的三项成本准备了一份预算草案，未确认的金额已标注。要查看吗？”草案只能使用实际读取到的材料；示例不代表当前产品已有该行为。

若无法读取草稿，只能说明“目前无法确认进度”；不能据此宣称用户未完成。若到了周四约定时间，即使没有新证据，也应按约定询问。用户确认完成后停止跟进；仅发现一份草稿不等于交付完成。

### 价值验收

一次帮助至少满足一项：节省了一次手工检查；提前指出可核验的阻塞；准备了被用户采用的材料或下一步操作。仅发送到期催促不足以证明产品价值。

## 3. 三阶段路线

| 阶段 | 用户获得什么 | 必须完成 | 暂不包含 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| Phase One：接住一件事 | 一个项目事项有人持续跟进，联系时带具体帮助 | 有边界的委托、内部来源取证、事件检查、下一步材料、可取消、可靠通知 | 外部数据源、综合画像、隐式偏好自动学习、长期 Goal 系统 | 单事项端到端验收通过，并在小范围试用中观察到实际价值 |
| Phase Two：少教、少管 | 多事项协作时减少重复解释、纠错和设置负担 | 带场景的偏好、知识与行为反馈、低负担关注视图、可选汇总 | 无证据人格推断、自动覆盖 USER.md、广泛生活追踪 | 跨会话偏好真实生效，纠错和管理负担下降，试用留存有证据 |
| Phase Three：延伸到真实工作环境 | 从一个外部来源获取进展，在授权范围内准备或执行下一步 | 单一只读集成、权限撤销、来源时效、选定动作的执行与验收 | 一次接通邮箱/日历/联系人、无边界自治、健康情绪监控 | 首个外部场景证明比内部场景新增价值，写操作另行评审 |

这是验收顺序，不是工期承诺。Phase One 也要从“委托 → 检查 → 有用材料 → 反馈 → 结束”贯通后再扩展；不能先交付空列表、开关或只有定时器的半成品。Phase Two、Three 仍为路线规划。

## 4. 共用产品规则

### 4.1 授权

- 开启主动模式只启用能力，不自动授权扫描历史、创建跟进或执行外部动作。
- 用户明确委托本身可构成事项级授权，范围清楚时不重复确认；模型从闲聊推测的需求只能在当前会话提出一次建议，接受前不创建持久跟进项或调度事件。
- 事项级授权覆盖指定来源的只读检查、约定范围内的分析和草稿准备；来源、执行权限、通知对象或有效期实质变化时才重新确认。
- 外部发送、发布、删除、付款及其它写操作仍走既有审批；“跟进”不提升权限。
- 关闭主动模式后停止本功能的检查与通知，保留状态供查看；独立创建的 Runtime Task 不受影响。界面必须明确区分两者。重新开启时不批量补发过期消息。

### 4.2 证据与未知状态

- 事实、模型推断和近期状态分开，保留来源、读取时间和适用范围。
- 无新信息、读取失败、工作未完成是三种不同状态。缺证据时不得编造进展、阻塞或成功。
- 约定的固定提醒必须兑现；只有条件性建议才可因无有效信息而沉默。模型失败不应吞掉明确提醒，使用结构化事项生成基本提醒并报告未能核查进展。
- 来源失效时按委托约定提示或等待；不擅自增加数据源、改为反复询问用户。后续来源权限撤销后立即停止读取，提示需调整或暂停委托。

### 4.3 打扰与反馈

- 用户明确指定一个通知目标，不自动挑首个绑定渠道，不将私人事项发到共享群。
- 安静时段、每日额度、事项冷却和去重由确定性规则约束。固定提醒与安静时段冲突时在创建时说明并确认处理方式，不能承诺原时间后静默延后。
- 首版不提供紧急突破免打扰。条件性建议超额时延后或进入已启用的汇总；固定提醒按创建时约定执行，其投递计数与条件性建议分开。
- “稍后”只改变当前事项的下次检查时间，不能一次就推导长期作息；未读、未点击不等于拒绝或完成。
- “停止跟进此项”和“关闭某类建议”分开。类别调整必须显示具体范围，可撤销；不能只改成继续发到摘要。
- 不因三次延后或长期无回复自动取消。按委托有效期结束；需要续期时提出明确选择。

## 5. Phase One：接住一件事

### 5.1 范围与入口

首个闭环只使用 Molibot 内的一个项目、关联 Plan/执行结果和用户指定产物。来源适配必须在同一阶段贯通，不能假定独立的 Mini App Todo 已接入。

用户可在对话中直接委托，或接受 Momo 的一次跟进建议。设置中启用能力后，从当前事项确认来源与通知目标；首次使用只填写无法从明确指令中获得的必要信息。

默认策略为草案建议，正式实施前纳入评审：主动模式默认关闭；启用时确认时区与安静时段（可预填本地 22:00–09:00）；条件性立即建议每天最多 2 条、同事项至少间隔 24 小时；每日汇总默认关闭。检查时间按事项约定，不要求统一“每天醒一次”。设置支持调整，但不向首次使用堆叠全部高级选项。

### 5.2 一份最小委托

| 内容 | 必须回答的问题 |
| --- | --- |
| 归属与范围 | 哪个 owner、Agent、项目负责？允许读取哪些具体来源？ |
| 预期结果 | 要交付什么？什么证据可以说明完成？哪些需要用户验收？ |
| 检查约定 | 看什么变化？何时检查？是否有固定询问时间？ |
| 无法判断时 | 等待、按约定询问，还是告知来源不可用？ |
| 可做的帮助 | 只读分析、清单、下一步建议、独立草稿分别是否允许？ |
| 联系方式 | 发到哪里？采用什么安静时段和提醒策略？ |
| 生命周期 | 何时开始、暂停、到期、完成或取消？ |

数据结构保留稳定事项 ID、授权记录、来源引用、关联任务/执行 ID、最近证据与判断、下次检查时间、有效期、投递去重标识。字段名和表结构由实施设计确定，不在 PRD 预设另一套任务引擎。

候选不成为已激活事项；确认后生命周期为 `active / paused / completed / cancelled / expired`。`nextCheckAt` 承载延后，不另造长期“稍后”状态。事项完成不自动将关联 Plan 标为验收完成，关联执行完成也只作为证据，按约定判定或请求用户验收。

### 5.3 检查、准备与通知

1. 来源事件发生、事项到期或约定检查时间到达，复用 watched event JSON 与运行时事件调度。
2. 先检查授权、生命周期、增量变化、权限和去重；没有条件性候选时不调用模型。约定提醒到期本身就是有效候选。
3. 有必要时做一次有预算的只读分析，输出结构化决定：保持安静、待汇总、通知。下一步建议或材料是通知的内容，不另设可绕过权限的动作类型。
4. 在已授权范围内准备缺口清单、决策选项或独立草稿。不得改写原文件或用户维护的计划；需要执行的建议由用户确认后交给现有执行链路。
5. 投递前重新校验授权、事项版本、通知规则；消息包含事实、为何此时联系、可直接采用的帮助、必要来源和操作。
6. 接受完成、延后、暂停、取消反馈，持久化后停止或调整检查。执行失败或暂未落盘时，不宣称已安排或已更改。

草稿必须可查看并区分来源事实与待核实内容；保存在隔离的派生产物中，关联事项及证据版本。来源权限撤销后不得继续展示受限内容，删除事项时清理本功能的派生副本；不删除原始项目文件或独立执行记录。

### 5.4 最小可见性与交互

沿用项目/任务入口展示跟进事项，实施设计时确定具体承载位置，避免新增重复导航。无论列表位置如何，必须支持查看委托范围、来源状态、最新判断、下次检查、有效期，以及暂停、恢复、完成、取消、删除。

消息按情境提供少量操作：待办型为“完成 / 延后 / 停止跟进”；材料型为“查看草稿 / 调整建议”。“有用”可选，不要求每条消息评价。需要执行时展示具体动作再确认。

Desktop/Web 提供管理入口，用户选择的一个既有私聊渠道完成通知与反馈闭环；使用既有渠道适配能力，其它渠道不自动接收。渠道不支持按钮时提供明确文本回复入口，状态变更统一走共享服务。无需逐个开启所有外部渠道验收。

### 5.5 Phase One 验收

| 场景 | 可核验结果 |
| --- | --- |
| 闲聊提到未来愿望，未接受建议 | 无持久跟进项、无调度事件，无重复推销 |
| 明确委托并成功保存 | 只创建一个事项，可查询授权与下次检查；保存失败不承诺成功 |
| 指定来源出现真实缺口 | 引用实际证据，准备可打开的清单或草稿；不改原文件 |
| 来源不可读或没有更新 | 显示未知，不推断未完成；按无信息约定处理 |
| 到达固定核对时间，无新进展或模型失败 | 仍兑现基本提醒；说明进展未核实 |
| 条件性候选无变化，或处于安静时段 | 不无故调模型或发消息；延后有真实状态 |
| 用户延后、完成、暂停或取消 | 下次检查和投递真实改变；忽略消息不改变完成状态 |
| 来源撤权、事项删除或授权到期 | 后续读取和投递停止；受限派生内容不可再访问 |
| 并发触发、服务重启、回执不确定 | 不重复建项；复用通知去重和补跑窗口，明确不确定投递 |
| 另一个 Session 继续讨论同一事项 | 读取同一委托及最新证据，无需重新完整交代；跨 owner/project 无越权读取 |

## 6. Phase Two：少教、少管

目标：在 Phase One 已证明有用后，支持多事项和跨会话协作，降低用户纠错与管理成本。

### 交付范围

- 复用现有 Memory/Profile，保存明确的协作偏好并进入真实回答与草稿生成路径；偏好带来源、场景和时效，例如“项目进度汇报简短”不泛化为所有回答都简短。
- 新的明确偏好仅在相同主题和适用范围内替代旧偏好。推断与事实分开，不因为两次纠正就认定永久习惯。
- 复用既有低风险候选自动确认能力，默认不悄悄启用；只有单独选择自动学习后，才允许经过评测的低风险推断生效，可查看、撤回。敏感信息不自动学习。
- 知识反馈修正事实，行为反馈调整联系策略；反馈显示影响范围，可撤销。一次延后不产生长期作息偏好，未读不进入负反馈训练。
- 提供“正在跟进 / 当前理解”视图：展示有来源的偏好、近期事项和错误纠正入口。不能自动覆盖 owner 维护的 USER.md，不输出缺乏证据的人格结论。
- 支持多事项合并通知与可选汇总；无内容不发。汇总受独立启用、退订、去重和过期规则约束，不成为被禁通知的旁路。

### 阶段验收

跨三个 Session 的同场景回复遵守明确偏好；相反的新指令及时生效，撤销后不再注入；工作偏好不污染其它场景。错误事实纠正后不会被旧摘要重新引入。类别退订与撤销可验证，汇总不重复推送已解决事项。

试用还应证明：用户重复说明减少；维护偏好、关注项和反馈的时间没有抵消收益。仅增加记忆条数、画像长度不算阶段成功。

## 7. Phase Three：延伸到真实工作环境

目标：为已验证的事项增加一个必要外部来源，再逐步允许有限执行。

### 7.1 先选择一个只读来源

按试用缺口选型：会议准备/时间冲突选日历；任务进度选实际使用的任务系统；材料准备选文档来源。不预先指定供应商，不把 MCP OAuth 协议打通视为真实第三方已接通。

本阶段需评审具体服务、账号、权限和费用。先完成读取、时效、撤销、来源失效与增量检查，证明增加了可采用的帮助；不批量接通邮件、联系人和浏览器。

### 7.2 再选择一种受控动作

从实际采纳的建议中选择一类动作，由用户确认目标和权限后交给现有 Runner/Plan/Durable 链路。展示将改什么、如何验证；只对具备可靠重试/幂等语义的动作自动恢复，不确定的外部提交不得盲目重发。

长期 Goal 与多个任务的关联，仅在试用证明单事项不足时另立范围；本阶段不承诺大型自治目标的动态拆解和连续执行。

### 阶段验收

一个真实来源在授权后可读、撤权后不可读；陈旧或失败输入不产生虚假提醒。选定动作有可核验产物与失败反馈，未授权不执行，完成由真实证据和约定验收确认。生产第三方账号与付费模型只在专项验收授权后使用。

## 8. 实现边界与质量要求

- 跟进项表达委托责任，Memory 表达已知信息，Runtime Task 表达确定调度，Plan/Durable 表达执行；关联既有对象，不复制其业务状态机。
- 业务与授权在共享 Agent/Runtime 层；Channel 只负责消息与交互转换。调度最终走 watched event JSON 和运行时事件，不写 OS scheduler，不以记忆替代任务。
- 内部检查是有预算的独立运行，不持久化为普通长寿命聊天；临时控制指令、用户提示和结构化排障记录分离。无有效候选直接结束，不扫描全部历史，不循环自唤醒。
- 检查采用最小必要输入，外部文本不获得指令权限；来源的 `no_memory / not_searchable / turn_only` 保持原语义，明确委托是单独授权操作，不能借提取候选旁路留存。
- 授权、事项更新和去重采用原子操作与版本校验；重试不重复准备同一版本材料。消息投递沿用 at-least-once 边界，不承诺绝对只发送一次。
- 设置使用细粒度保存与临时数据库整对象 save → 新 store → load 回归。UI 遵循 DESIGN.md、既有 shadcn 组件、固定保存底栏，支持中英即时切换、明暗主题和窄窗。
- 修改内置 Momo 模板时 bump 版本，用户已改副本先备份。修改记忆或偏好注入时核对最终系统提示词，避免重复 section 和污染缓存稳定前缀。
- 测试使用隔离实例、临时数据和本地模拟模型；行为测试覆盖成功与失败，新增用例证明能捕获故障并连续运行 5 次通过。UI 必做隔离冷路径，涉及原生链路则补对应原生验证；无法执行的检查明确列为未验证。
- 每个实现单元只跑直接相关检查；全量 `pnpm verify:feature` 及原生整体验收由用户在专项验收或发布时主动执行。

## 9. 试用与产品验证

建议 Phase One 先由 owner 自用两周，再邀请 3–5 位确实在项目中使用 Molibot 的用户试用。人数与周期是验证方案，不是市场结论或开发排期。

| 指标 | 定义与用途 |
| --- | --- |
| 实际帮助 | 被采用的草稿/建议、节省的手工检查或提前发现的真实阻塞；以用户确认和证据为准 |
| 管理成本 | 配置、补充背景、纠错、反馈所花时间；与节省时间同时记录 |
| 持续委托 | 用户是否在后续一周主动继续或新增真实委托；不能用未关闭开关代替留存 |
| 误打扰 | 用户明确认为无关、过多或时机错误的通知，按原因分类；未读不直接计负反馈 |
| 可靠性 | 越权、虚假完成、失约提醒、重复建项和重复投递分别统计；目标为零，投递不确定单列 |
| 单位价值成本 | 模型与运行成本除以被验证的实际帮助次数；没有帮助时不得展示为低成本成功 |

进入 Phase Two 的建议证据：连续两周存在被确认的实际帮助，用户主动愿意继续委托，且管理成本低于节省成本；小样本只用于判断方向，不声称统计显著或已证明商业化。若效果仅为到期催促，应收窄场景或调整帮助方式，不靠增加通知频率补救。

付费验证在用户持续使用后进行：记录实际购买或明确试付费行为。口头“觉得不错”、通知点击和记忆数量不能代替支付意愿。

## 10. 实施评审前需定案

本 PRD 已给出推荐范围，以下是具体落地决策，不影响先评审完整方案：

1. 选一个真实项目事项和成功产物，确认 Phase One 最小来源适配能获取所需证据。
2. 确认首个试用的私聊通知渠道、安静时段及固定提醒冲突处理；不得默认绑定任意可达渠道。
3. 在现有项目/任务界面确定最小管理入口，按 DESIGN.md 补交互设计。
4. 根据专项验证和试用数据决定是否进入下一阶段；Phase Three 再选择外部服务、账号与费用。

本次范围是产品方案整理。实现排期、Issue 分派、第三方授权和部署分别在相应评审后确定。
