# Durable 唤醒队列与执行器硬化 Spec

## Problem Statement

Durable Execution 已经能跨 Execution Attempt 推进长任务，但在“排队 → 运行 → 恢复”的边界上，用户和运维会遇到四类可感知故障：

1. **崩溃后停在排队中**。Execution Step 结束后执行状态已经提交为待继续，但让下一步真正跑起来的动作是提交之后的一次目录扫描加事件文件写入；进程在这两步之间退出，计划就停在“排队中”，只能等下一次重启扫描，或由人发现后手动恢复。
2. **恢复粒度太粗**。一次 Execution Attempt 中途崩溃后，整个 Execution Step 被标记为不确定；即使前面若干工具已经成功并有回执，用户仍可能被要求从头重跑，或者被一个不必要的恢复确认卡住。
3. **长步骤被抢走**。Execution Attempt 的租约从不续期，且租约时长与事件超时共用同一个设置。步骤运行时间一长，租约在运行中过期；更严重的是，第二个进程启动时会按“租约不是本进程”直接接管，而不管租约是否仍有效。
4. **卡住时说不清原因**。计划详情只有进度投影，没有租约剩余、待唤醒记录、不确定步骤原因和阻塞原因。用户看到“运行中/排队中”，运维只能翻日志拼时间线。

这四类问题对用户表现为“计划偶尔需要人工救”“长任务不可靠”；对维护者表现为“每新增一条写路径，都要记得手动触发一次调度”“finalize 撞上并发审批会把 Attempt 留在运行中直到下次重启”。

## Solution

把 Durable Execution 的唤醒从“提交后扫描目录 + JSON 事件文件”改为**与状态变更同一事务写入 SQLite 唤醒表，由 claim + worker 消费**；同时补齐租约心跳、CAS-safe finalize、存储错误分级、工作进度检查点、取消级联和执行器诊断视图。产品语义（副作用分级、幂等键、审批、验收标准、Task Budget）保持不变。

用户可感知的变化：

- 进程在任意时刻崩溃，计划都能在重启后自愈，不需要人工“恢复”。
- 长步骤不再因为租约过期被另一个进程接管；第二个进程启动不会误杀正在跑的计划。
- 工具检查点说明最后完成的位置；当前整步重试必须检查整步副作用，不能凭其他工具的完成时间放行。
- 取消计划会一起停止它派生的子会话与子代理，不会留下后台工作。
- 计划详情新增“诊断”视图，能直接看到阻塞原因、租约剩余、下次唤醒时间。

## User Stories

1. 作为计划所有者，我希望一个执行步骤结束后下一步一定会被调度，以便进程在任意时刻崩溃都不会让计划停在“排队中”。
2. 作为计划所有者，我希望重启后计划自动继续，而不是收到“需要手动恢复”的提示。
3. 作为计划所有者，我希望已发生或结果未知的外部操作不会在恢复时自动重放；整步重试不能跳过必要的外部核对。
4. 作为计划所有者，我希望只有可能改写外部状态的操作才需要我确认，纯读取和可重复操作自动继续。
5. 作为计划所有者，我希望看到一个明确的阻塞原因（等待审批、等待决定、租约、验证失败、预算），以便决定继续还是取消。
6. 作为计划所有者，我希望取消计划时它的子会话和子代理一起停止，以便不在后台留下仍在运行的工作。
7. 作为计划所有者，我希望重复点击暂停或取消是幂等的，不会产生第二次外部副作用。
8. 作为计划所有者，我希望长步骤（超过十分钟）不会因为租约过期被另一个进程抢走。
9. 作为计划所有者，我希望计划详情显示下次唤醒时间和排队位置，以便判断它是否真的在推进。
10. 作为计划所有者，我希望唤醒记录被保留一段时间，便于事后解释“这一步为什么重试过三次”。
11. 作为计划所有者，我希望验收标准仍然由确定性检查器判定，调度改造不改变验收语义。
12. 作为计划所有者，我希望计划完成或阻塞的通知只发送一次，重试不会重复打扰我。
13. 作为渠道用户，我希望计划在后台推进时不会占用我的会话上下文，完成后只收到一条结果。
14. 作为运维，我希望启动第二个进程时不会误杀另一个进程正在执行的计划。
15. 作为运维，我希望系统能检测到“同一份存储被两个实例同时写入”并明确拒绝启动，而不是悄悄抢租约。
16. 作为运维，我希望存储损坏、磁盘写满等致命错误让执行器快速停止并等待重启，而不是在坏状态上继续接新计划。
17. 作为运维，我希望明确知道当前使用文件事件、SQLite 唤醒表还是双轨调度。
18. 作为运维，我希望迁移日志给出扫描、入队、过期、丢弃、失败的精确数量。
19. 作为运维，我希望事件目录不再随版本推进无限增长。
20. 作为运维，我希望诊断视图能看到租约归属与剩余时间、已认领的唤醒、不确定步骤与原因。
21. 作为运维，我希望进程正常退出时释放自己的租约，重启后不需要等待租约自然过期。
22. 作为开发者，我希望“调度”是存储层的不变量，新增一条写路径时不需要记得手动触发调度。
23. 作为开发者，我希望同一个执行版本最多只有一条待消费的唤醒，旧版本的唤醒自动作废。
24. 作为开发者，我希望并发 claim 只有一个赢家，并有自动化测试证明。
25. 作为开发者，我希望 finalize 遇到版本冲突时自动重读并重试，而不是把 Attempt 留在运行中。
26. 作为开发者，我希望错误按“存储错误 / 请求错误 / 业务错误”分级处理，而不是在 catch 里一律转恢复。
27. 作为开发者，我希望 worker 只负责调度，不自动重放有副作用的步骤。
28. 作为开发者，我希望迁移是幂等的，可以在每次启动时安全重跑。
29. 作为开发者，我希望从数据库模式回滚到文件模式不需要数据迁移。
30. 作为开发者，我希望执行语义有版本号，未来变更时可以迁移在途执行。
31. 作为开发者，我希望热路径不再为了拿一个版本号而全量加载执行的全部子表。
32. 作为开发者，我希望存储实现的拆分是纯搬家，不改变任何外部行为。
33. 作为审计者，我希望每条唤醒记录都保留尝试次数、认领者、最后错误和时间戳。
34. 作为审计者，我希望成功和作废的唤醒按保留期清理，失败的唤醒长期可见。
35. 作为安全负责人，我希望旧事件文件迁移只接受版本匹配且仍可继续的执行，过期或终态的一律丢弃。
36. 作为未来的云端部署者，我希望调度真相在数据库里，而不是本地目录，以便存储迁移时不重写调度逻辑。

## Implementation Decisions

1. **单一调度真相**：新增一张唤醒表，与执行状态同库。每条唤醒以“执行 + 期望版本”为唯一键，保存原因、计划时间、状态、尝试次数、认领者与错误。执行版本的推进只产生新的唤醒，旧版本的待消费唤醒立即作废。按 ADR 0004，带状态机、并发与崩溃恢复语义的状态必须落在数据库而不是 JSON 文件；唤醒由 Durable Execution 这一聚合拥有、并与执行状态同事务写入，因此放在同一个有界上下文的数据库文件里，而不是另起一个文件。
2. **事务内入队**：所有让执行重新可跑的写入（Attempt 结束、状态转移、容量延后、恢复、控制动作、计划批准）都在同一个事务里写入唤醒；不再依赖提交后扫描目录。扫描保留为启动兜底与迁移工具。
3. **唤醒原因枚举**：推进、验收、容量、恢复、控制、重试。原因只用于观测与退避策略，不参与状态机。
4. **状态机**：待消费 → 已认领 → 完成 / 作废 / 失败；可重试失败回到待消费并按指数退避，业务失败不回队。

   ```text
   待消费 ──认领──▶ 已认领 ──执行成功──▶ 完成
      ▲                 │
      │                 ├─ 版本不符 / 执行已终态 ──▶ 作废
      │                 ├─ 可重试失败且未超限 ──▶ 待消费（退避）
      │                 └─ 不可重试 / 超限 ──▶ 失败
      └── 新版本推进写入新行（同版本唯一，重复入队幂等）
   ```

5. **认领语义**：认领在立即事务里完成，按计划时间先进先出；并发认领只有一个成功者，其余看到零行受影响。同一执行同一时刻至多一条已认领唤醒。
6. **worker**：新增独立的唤醒 worker，按秒轮询并在进程内提交后立即被唤醒；按空闲执行槽认领、逐条执行、按结果结算；慢任务不阻止其他空闲槽接收新任务。关闭时等待在跑的唤醒结束；其他进程未结算的过期认领由独立维护周期回收，活跃尝试及本 worker 的在途认领不回收。
7. **重试与退避**：worker 只重试进程级瞬时错误（存储忙、运行器重建失败），退避为指数增长并带抖动，默认最多五次；业务失败（模型、工具、验证）由运行时写终态，worker 不再重放。
8. **唤醒保留**：完成与作废保留七天（可配置），失败长期保留并在诊断视图可见。
9. **租约与心跳**：Execution Attempt 持有期间按租约时长的三分之一续期；续期失败立即中止本次 Attempt，不再写业务终态。租约时长成为独立设置，不再复用事件执行超时。
10. **恢复判定**：只回收“归属不是本进程且租约已过期”的 Attempt。启动时写入实例租约；若另一实例的租约仍有效，暂不消费并周期重试启动。实例续期与孤儿回收独立于任务执行，使用同一实例租约时长，启动时未过期的孤儿也能在过期后恢复。正常退出释放自己的租约。这条与 ADR 0005 的“每个 Pi 存储实例只有一个活跃服务所有者、不声称分布式保证”一致，并把该假设从注释变成运行时保护。
11. **finalize 硬化**：终态写入遇到版本冲突时，重新读取当前版本并重试（默认三次）；三次仍冲突则走致命错误处理，禁止吞掉后留下运行中的 Attempt。
12. **错误分级**：存储错误（I/O、损坏、写满、只读、反序列化失败）视为致命：停止认领、结束所有等待、发布关闭信号交给上层重启；未知执行、版本冲突、非法状态转移只失败当前调用；业务错误只失败当前 Attempt。
13. **进度检查点**：每个工具调用结束记录一条 Attempt 级进度（序号、调用 ID、工具、状态、摘要）。检查点用于诊断，不替代逐项副作用核对。当前恢复重新执行整步：纯读取和可重复操作允许重跑，可查询操作走外部状态探针，含非幂等操作的步骤先转人工核对；其他工具完成或已有回执均不意味着整步可安全重放。
14. **取消级联**：暂停或取消计划时，先中止当前 Attempt，再枚举并中止该计划派生的子会话与子代理，等待工具静默后写入终态。无法停止派生工作时进入恢复状态并报告，不假装已停止。
15. **诊断视图**：新增只读诊断，包含租约归属与剩余、待消费与已认领唤醒、不确定步骤、阻塞原因、最后完成的工具、队列位置与下次唤醒时间。计划详情页提供入口。
16. **迁移**：启动时扫描旧的 durable 事件文件，解析执行与版本；执行不存在、版本不匹配或已终态的丢弃，其余入队后删除文件。迁移幂等，可重复执行；单个文件失败不阻塞启动，移入失败目录并在下次启动重试。
17. **双轨与回滚**：配置支持“文件 / 数据库 / 双轨”三种模式；双轨期两条路径都可能触发，但版本比对保证重复触发无害。数据库模式稳定两个版本后删除文件路径；回滚只切换模式，不做数据迁移。
18. **存储基线**：启用 WAL 与 NORMAL 同步；热路径改为窄查询，不再为取版本或当前步骤而全量加载执行的所有子表；执行记录增加引擎版本，供未来语义迁移。
19. **模块改动范围**：Durable Execution Store（新表、入队、认领、租约、finalize、窄查询）、Durable Execution Runtime（worker 接线、恢复、错误分级、取消级联、诊断）、唤醒 worker（新增）、Plan Service / Coordinator（去掉手动调度责任）、事件监视器（仅保留迁移与兜底）、设置（租约与调度模式）、桌面计划接口与详情页（诊断）。
20. **不变式**：任何 Attempt 进入运行后，终态必须由 finalize、恢复或致命错误三者之一落地；不存在“写完开始就再没人负责”的路径。
21. **兼容性**：副作用分级、幂等键、审批范围、验收标准、Task Budget、Evidence 语义全部不变；现有计划数据无需迁移。

## Testing Decisions

**什么算好测试**：只断言外部可观察行为——执行状态、唤醒表状态、Attempt 数量与终态、租约归属、执行次数、诊断字段——不断言私有方法或 SQL 细节。使用真实 SQLite 临时文件而不是内存桩；需要并发时用两个 Store 实例指向同一文件来模拟两个进程；需要时间推进时注入时钟，不 sleep；崩溃用“在指定提交点抛出/中断后重新打开”的方式模拟，保持确定性。

**已确认的测试接缝（三个）**：

1. **Durable Execution Store 公共 API（主接缝）**：临时 SQLite 文件。覆盖事务内入队、认领并发、版本作废、退避与上限、租约续期与过期回收、finalize 冲突重试、致命错误分类。
2. **唤醒 worker（注入时钟与执行函数）**：覆盖轮询与提交唤醒、批量认领、退避排期、关闭等待、未结算认领的回收。执行函数用桩替代真实运行器。
3. **迁移函数（临时目录 + Store）**：覆盖解析、版本校验、终态过滤、幂等重跑、失败文件隔离、日志计数。

**被测模块与关键用例**：

- Store：同事务入队；100 个并发认领恰好一个成功；旧版本唤醒作废；退避上限；租约未过期不得回收；过期可回收；冲突重试后成功。
- Runtime：崩溃后重启自动继续；仅重跑不确定区间；取消级联到子会话与子代理；致命存储错误停止认领并结束等待。
- Worker：提交后即时唤醒；批量与 FIFO；关闭不丢在跑项；重启回收已认领。
- 迁移：混合文件（有效、过期、未知执行、终态）得到正确计数与结果；重复启动不重复入队。
- Plan Service / Coordinator：状态转移后不再需要调用方手动调度。

**先例**：现有 Store 与 Runtime 的回归、并发用例，协调器用例，以及基于真实进程强杀的恢复矩阵，都是同类测试的参考；新增用例遵循它们的“临时目录 + 真实 SQLite + 确定性时钟”风格。

**验收门槛**：新增唤醒与硬化用例不少于十五项；类型检查零错误；服务启动、桌面对话、项目、决策四组既有回归全绿；迁移日志与诊断字段可被自动化断言。

## Out of Scope

- 不改造其他内部事件（记忆反思、每日素材、会话自动归档、周期任务、用户可见提醒）的文件事件体系。按 ADR 0003，Runtime Task 仍是 watched-event JSON 的 CRUD 聚合；本次只把 Durable Execution 的触发器移出文件层。
- 不迁移会话历史存储。
- 不引入外部文档/复制/分叉框架。
- 不为多实例部署做存储抽象或异步数据库门面；本 spec 明确单写实例，并用实例断言保护。
- 不改变副作用分类、审批范围、验收标准、Task Budget 的产品语义。
- 不做计划详情页的整体改版，只增加诊断入口。
- 不自动重放有副作用的步骤；恢复仍以 Safe Resume Point 和 Side-effect Record 为准。
