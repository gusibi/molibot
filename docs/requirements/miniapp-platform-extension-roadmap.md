# Mini App 平台扩展路线图

> 性质：方向性文档，不是实施方案。每条能力真正动工前需要单独的技术方案/PRD。
> 维护约定：某条能力立项后，把状态改为链接到对应方案文档；被否决的条目移到 §5 并写明理由，防止反复重提（参考 memory 惯例：拒绝过的方案要留痕）。

## 1. 心智模型：缝的清单

Mini App 与主程序之间的每一条连接都必须是一条**显式的、经过 `MiniAppHost` 或既有共享层的缝**。当前全景：

| # | 方向 | 缝 | 状态 |
|---|------|----|------|
| 1 | 模型 → App | Agent 工具 `miniapp__<appId>__<tool>` | ✅ 已交付 |
| 2 | 用户 → App（经模型） | `@app` 选择器路由 | ✅ 已交付 |
| 3 | App UI → App 服务端 | `/miniapps/<id>/api/*` | ✅ 已交付 |
| 4 | 宿主 UI → App（确定性，无模型） | 消息/附件/选区动作 | ✅ `docs/archive/requirements/miniapp-message-actions-plan.md`（2026-08-06） |
| 5 | App UI → 宿主 UI | postMessage 桥（composer 填充 / 附件 / 跳会话） | ✅ v1（2026-08-06）+ v2（2026-08-07），见 `docs/archive/requirements/miniapp-composer-bridge-plan.md` |
| 6 | App 服务端 → 宿主模型能力 | AI 门面 `ctx.ai` | ✅ 平台链路；⚠️ 麦克风人工矩阵待验收，见 `docs/archive/requirements/miniapp-ai-facade-prd.md` §7 |
| 7 | App → 宿主展示面 | 结果卡片 + 深链 + 侧栏徽标 | ✅ 2026-08-07（本文档 §2.3/§2.4/§2.5） |

新场景先问：它是哪条既有缝的延伸？只有回答"都不是"时才允许开新缝。

## 2. 近期梯队（与已立项方案共享大部分基建，随时可立项）

### 2.1 渠道侧同构动作
飞书/Telegram 里对 bot 消息回特定 emoji 或 `/fav` 命令 = 缝 4 的同一个 capture 契约。捕获逻辑放共享层，渠道层只做消息搬运（分层规则）。价值：收藏行为不再局限于桌面。

### 2.2 桥动作集延伸（缝 5 升 version）— ✅ 已交付（2026-08-07，Bridge v2）
- `composer.attach`：App 把处理完的文件（编辑好的图、导出的纪要）填充为 composer 附件——图片编辑场景的回程路，和缝 4 Phase 2 的去程正好闭环。
- `chat.openSession`：配合深链（§2.4）从 App 面板跳转到某个会话。

**实施记录**：v1 与 v2 同时受支持，且**动作集按 version 冻结**——v1 只有 `composer.insert`，v1 消息请求 v2 动作报 `unsupported_action`。已装的 v1 App 不需要改动。`composer.attach` 的 `path` 是 App dataDir 内的相对路径，宿主 `readDataFile()` 跟随符号链接后校验包含性再读取（≤32 MiB），WebView 全程拿不到宿主路径。桥依旧只搬运 UI 意图：没有任何动作能发送消息或触发 Agent 轮次，这条纪律有结构守卫断言。

### 2.3 结果卡片 — ✅ 已交付（2026-08-07）
工具结果目前是纯文本；允许 App 声明一个轻量卡片渲染（收藏成功后消息下方直接显示卡片、会议纪要完成后显示摘要卡）。约束：卡片是**展示**，卡片内的交互一律跳 App 面板，不在卡片里做写操作。

**与原设想的偏离（已决策）**：原文写「复用既有 iframe/CSP 边界」，实施时改为**宿主渲染的声明式卡片**（`src/lib/shared/miniappCard.ts`）。理由有两条：(a) 卡片出现在滚动的 transcript 里，每张一个 iframe 意味着不设上限的活文档；(b) 更关键的是 iframe 什么都能做，与同一段话自己的约束「卡片是展示、交互一律跳面板」直接冲突。固定的声明式结构让这条约束**由构造成立**——`MiniAppResultCard` 里没有任何能写入的控件，唯一出口是深链。宿主统一 sanitize（标题 120 字符、最多 6 条 field、图标白名单、`link` 必须指向声明它的那个 App），越界只丢弃卡片内容，绝不让已经成功的工具调用失败。`content` 仍是权威文本——模型只读它，非桌面端也只显示它。

### 2.4 深链 — ✅ 已交付（2026-08-07，进程内路由）
`molibot://miniapp/<id>/<path>` 打开 App 面板并定位到具体条目。用途：结果卡片"查看详情"、通知点击落点、纪要里引用某条收藏。宿主只定义"打开面板 + 把 path 交给 App UI"，语义归 App。

**实施记录**：链接被解析成一个**意图**并在进程内路由，永远不会交给 WebView 去导航（卡片上的是 `<button>` 不是 `<a>`）。`path` 作为 `?path=` 启动参数随 `locale`/`theme` 一起给 App UI，不拼进资源路径。解析**不走 `new URL()`**——URL 解析器会先把 `..` 规范化掉，`molibot://miniapp/notes/../../etc/passwd` 会变成指向 `etc` 这个 App，一个声称打开 A 的链接静默打开了 B；必须看未规范化的原始串才能拒绝穿越。**本期未做**：OS 级 URL scheme 注册（需要 `tauri-plugin-deep-link` + Rust 改动）。当前所有消费方都在应用内，注册后只需把同一个 `parseMiniAppDeepLink` 接到系统入口即可。

### 2.5 App 徽标与轻通知 — ✅ 已交付（2026-08-07）
App 服务端置一个未读计数/状态点，显示在侧栏图标上（会议转写完成、周报生成好了）。刻意做小：**不做**系统通知、不做打断式弹窗——App 的"完成"通过徽标 + 面板呈现。若要进对话，走 §3.2 的事件缝，不另开口子。

**实施记录**：`ctx.badge.set/get/clear`，`{ kind:"count", count }` 或 `{ kind:"dot" }`。计数上限 99，`count <= 0` 视同清除（倒数到零应该没有徽标，而不是一个 "0" 标签）。**只存在内存里**：重启后不可能还有进行中的工作，恢复一个没有依据的计数正是 pitfall #23a/#23d 那一类错误。写入方只有 App 服务端——桌面路由只能 `clear`，两个写入方就是宿主与侧栏各说各话的开始。用户打开面板即清除（"看到了"这件事只有宿主知道），且清除后应用的是服务端返回的整份 catalog，不在本地猜。被停用/加载失败的 App 不再对外报告徽标。

## 3. 中期梯队（平台价值大，但各有一个需要想清楚的核心问题）

### 3.1 App 作为 Agent 上下文提供者（"存"变"用"的价值闭环）
App 声明（或约定实现）一个 `search` 只读工具，Agent 回答时可检索 App 数据——"我收藏过什么关于 X 的""上次会议里谁负责这件事"。这是收藏夹/会议记录真正的价值兑现。核心问题：与既有 memory/检索体系的关系（是注册成 Agent 可选工具，还是进 context 组装管线）；CJK 相关注意 pitfall #8（用 `moryTokenize`）。

### 3.2 App 事件 → 会话（App 主动说话）
App 完成长任务后向某个会话注入一条系统注记（"纪要已生成，@meeting-notes 查看"）。核心问题：这是第一条 App **主动**进入对话流的缝，必须复用会话注记/automation 的既有语义，且绝不能伪装成 assistant 回复（pitfall #14c：status 不是 content 的同族纪律）。

### 3.3 App 定时任务
manifest 声明周期任务（每周日收藏回顾、每天早上待办摘要），复用 events/lease 调度基建。**刻意押后**：调度层刚经历 #23 的整轮加固，让它先稳定运行一段时间再向第三方代码开放。开放时直接继承 owner_id 收养、时间窗补跑、终态化那一整套纪律。

### 3.4 联邦搜索
宿主全局搜索聚合各 App 的 `search` 工具结果。依赖 §3.1 先定下 `search` 约定；UI 上是搜索面的改造，单独排期。

### 3.5 AI 门面 v2
流式输出（长纪要生成的体验）、图像识别/生成能力、embedding（供 §3.1 的 App 做自己的向量检索）。按 `docs/archive/requirements/miniapp-ai-facade-prd.md` §9 的非目标清单逐个解锁。

## 4. 远期/待观察（记录想法，暂无立项计划)

- **App 间调用**：收藏夹调提示词库的工具。命名空间已隔离（`miniapp__<appId>__`），技术上不难，但会引入 App 间依赖图与卸载顺序问题，等出现真实需求再设计。
- **导入/导出约定**：App 数据的标准备份契约（manifest 声明 `export` 工具），配合宿主统一的备份入口。
- **宿主级录音/语音输入**：若 AI 门面的麦克风 spike 走到 B/C 路线，宿主级录音能力可以反过来服务所有 App 和主程序自己的语音输入。
- **拖拽**：把消息/附件拖到侧栏 App 图标上 = 缝 4 的另一个入口，纯 UI 增强，等缝 4 Phase 2 落地后看使用习惯。
- **Composer 结构化快捷表单**：App 贡献 `/命令` 式的快捷表单（记账弹个金额+分类小表单）。与既有命令/Skill 胶囊体系有交叠，需要先理清三者的定位再动。
- **App 市场/分享**：GitHub 安装已支持；目录、评分、更新通知等等出现多个第三方 App 后再谈。

## 6. 排期建议

```
消息动作 Phase 1 → Composer 桥 v1 → 消息动作 Phase 2（附件/选区）  ✅
                                      ↘
                         AI 门面（文本先行）✅ → 麦克风 spike ⚠️ → AI 门面（转写）✅ + 会议记录参考 App ✅

Bridge v2 + 结果卡片 + 深链 + 徽标（§2.2–2.5）  ✅ 2026-08-07
```

剩余近期项：§2.1 渠道侧同构动作（唯一未动工的近期梯队条目）。

三条已立项方案彼此无硬依赖，可并行交给不同执行者；但消息动作 Phase 1 建议最先——它建立的"贡献点 + 宿主直接调用"模式是后面多数能力的心智基础。
