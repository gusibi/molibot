# 对话统一过程区与完整最终结果

日期：2026-10-29。优先级：P1。阶段：已实现，隔离定向验收。

执行跟踪：[GitHub Issue #69](https://github.com/gusibi/molibot/issues/69)，标签：`ready-for-agent`。本版实现采用统一折叠过程区、显式结果提交和共享完整交付规则；验收记录见下文。

## Problem Statement

用户需要阅读完整结果，也需要在等待、审批和排错时了解执行情况。将正文与工具节点逐个交替展示，会让多工具任务出现大量“已完成操作”入口，割裂阅读；将最后一次模型消息直接作为结果，又可能只留下“已经记下了”，遗漏真正的回答和追问。

已核验的原始案例为：思考 → 完整回答及追问 → 保存记忆成功 → 简短确认。完整回答被折叠不是记录丢失；最后一条消息也不足以独立回答用户。问题同时涉及结果生成和界面信息层级，不能只靠调整折叠位置解决。

当前代码可能已按上一版 spec 改为正文与工具节点交替显示。该行为不是本版目标，执行 agent 应以实际工作区为准，不沿用文档中的旧实现判断。

## Solution

一轮对话只有一个助手回答容器，其中包含一个统一过程区和一个独立的最终结果区。

- 过程区集中容纳进度说明、模型返回的思考、工具调用及结果，内部保留真实类型和事件顺序。工具调用不在结果正文中产生独立披露入口。
- 运行时显示简短真实进度，用户可展开过程查看详情；完成后过程默认收起。入口使用“查看过程”等能涵盖思考和执行的名称，不能将工具日志伪装成模型思考。
- 最终结果区完整回答用户，包含必要结论、实际执行结果、限制以及需要用户回答的问题。用户无需展开过程即可理解结果并继续对话。
- 审批、等待用户输入和需要处理的失败直接可见。失败或停止不能抹掉已经形成的有效答案，也不能显示为成功完成。

“完整最终结果”不等于“最后一条模型消息”，也不等于“所有 text 拼接”。新执行链路必须形成明确、可持久化的结果语义；不能由界面根据工具前后位置猜测。

## User Stories

1. 作为对话用户，我希望每轮只看到一个最终结果区，以便连续阅读答案。
2. 作为对话用户，我希望调用十次工具也只有一个过程入口，以便界面不被执行节点切碎。
3. 作为对话用户，我希望最终结果独立回答原问题，以便不必展开过程补全信息。
4. 作为对话用户，我希望必要建议和追问出现在最终结果中，以便知道下一步该做什么。
5. 作为对话用户，我希望工具完成确认不会替代完整回答，以便同时获得答案和执行结果。
6. 作为等待执行的用户，我希望看到简短真实进度，以便确认任务仍在推进。
7. 作为对话用户，我希望按需展开一个过程区域，以便核验执行而不影响默认阅读。
8. 作为核验结果的用户，我希望过程内部保持事件顺序，以便理解每次调用及其前后说明。
9. 作为核验结果的用户，我希望思考、进度说明和工具记录有明确类型，以便不将工具结果当作模型思考。
10. 作为返回历史对话的用户，我希望已完成过程默认收起，以便优先阅读结果。
11. 作为查看过程的用户，我希望手动展开状态得到尊重，以便后续增量不会反复打断查看。
12. 作为需要批准操作的用户，我希望审批和待决定计划直接可见，以便及时处理。
13. 作为遇到失败的用户，我希望看见未完成事项和真实错误状态，以便判断是否继续。
14. 作为停止任务的用户，我希望有效部分结果仍然保留，以便不丢失中断前的工作。
15. 作为复制回答的用户，我希望复制完整最终结果，以便不带入执行日志或中间旁白。
16. 作为搜索回答的用户，我希望能找到最终结果中的结论与追问，以便定位可读答案。
17. 作为浏览会话的用户，我希望预览来自最终结果，以便不会只看到“我先查一下”。
18. 作为切换 Session 或恢复连接的用户，我希望结果、过程和状态一致，以便信任持久记录。
19. 作为普通聊天、项目聊天或外部只读会话的用户，我希望相同内容采用一致的展示规则，以便不同入口不会改变答案含义。
20. 作为中英文、明暗主题或窄窗口用户，我希望过程入口和结果都可读可操作，以便在不同环境下使用。

## Implementation Decisions

- 共享运行时负责形成结果，统一对话投影负责提供结果与有序过程，界面负责呈现。通用逻辑不能放到 Channel，也不能为 save_memory 添加特例。
- 新执行应明确区分进度说明、稳定答案片段和最终交付。先检查现有模型适配、事件及持久化接口能够保留的语义；不要假设各 Provider 都支持同一个 phase 字段。不能将普通 text 或 stopReason 自动等同于答案用途。
- 模型在工具调用前后的面向用户文字可以作为过程说明保留。工具阶段形成的有用结论和追问，必须在最终交付时纳入完整结果；不能要求用户去过程里寻找答案。
- 在真实工具循环结束后的结果生成环节明确要求完整交付，而非仅报告最后一次工具结果。所需提示与执行控制位于共享层；临时控制不得作为普通对话消息写入 Agent Context 或回灌后续轮次。
- 不通过字数、关键词、问号或工具位置判断最后一句是否完整。不得把所有 text 拼接作为最终结果，也不得增加独立语义分类器。结果收尾需有明确生命周期和预算，不允许无限续写。
- 若完成完整结果需要额外收尾模型调用，该调用仅用于整合已有输入与执行结果，撤下可执行工具，不得重跑工具或重复写入。优先复用正常工具后模型回复环节，避免每轮无条件增加模型调用。预算耗尽、取消、失败或等待审批时必须明确终态；不得为补总结越过这些状态启动新工作。
- 最终结果与原始过程独立保存其展示语义，重载时不得重新根据文本内容或工具位置推断。尽量复用现有持久化机制；若必须调整持久化结构或 API，在共享层一次完成并补临时数据库集成回归，不增加兼容层、fallback 或历史迁移脚本。
- 旧记录不会因重载自动触发模型请求或工具执行。已有明确结果语义的记录按语义展示；缺少结果语义的历史记录不可伪造“完整最终结果”。保留原始过程和已有末段，并在无法还原完整结果时明确显示历史结果未完整记录。历史自动总结、批量修复不属于本次范围。
- 每轮只渲染一个过程入口；思考、进度说明、工具参数、结果和日志在展开后按时间顺序呈现。思考使用与工具同轴的普通文本节点，用图标与可访问名称标识类型，不再复用独立思考折叠卡或增加第二层标题。可以在过程内部区分类型或压缩连续工具记录，但不得生成多个过程区穿插在最终答案中。没有过程时不显示空入口。
- 运行中使用同一过程区与简短状态行承载更新。最终结果可流式输出，必须具有明确答案语义；后续工具事件不能静默把已确认的答案降为过程。若执行生命周期不支持稳定答案标记，则将未定稿文字留在过程，收尾时再流式交付结果。
- 完成后过程默认收起；用户已手动展开时不反复强制收起。审批、待决定计划和需处理错误不藏在过程内。运行状态来自结构化事实，工具成功不代表整轮成功。
- 复制回答、结果搜索、索引及预览统一消费最终结果；部分失败时消费明确标记的有效部分结果。不混入思考、工具载荷或中间旁白。过程内容可供展开检查，新增过程全文搜索不在范围内。
- 实时、结束事件、历史查询和恢复使用相同结果语义与稳定身份，防止重复片段或完成后缩回一句确认。禁止根据字符串相同去重独立事件。
- 同步统一设计规范中的冲突条目：以“统一过程区＋独立完整结果”为准，撤回正文/工具交替、多张过程卡和单独思考入口的要求。在同一个 slice 应用到所有共用界面，保留既有组件、语义 CSS、主题与无障碍支持。

## Testing Decisions

- 优先在最高的现有共享运行时→持久化→对话投影入口，用本地脚本模型和临时 store 驱动完整轮次，断言最终交付、实际工具副作用与过程记录；另用直接相关 UI 测试验证折叠和可见性。复用现有测试框架，不新建验收平台。
- 参考现有 Runner、对话投影、多终止回复、中断回归及实时控制器测试。只验证对外行为，不用数组形状或源码字符串替代“结果完整”的断言。
- 核心案例：模型先给出建议和追问，保存记忆后只给简短确认。新运行必须产生含必要建议、追问和真实保存结果的独立交付；只显示确认、拼接全部旁白、将十个工具节点插入答案的实现都不能通过。
- 使用脚本模型显式控制工具前文字和收尾结果，不依赖真实模型随机行为。断言收尾收到必要上下文、处于正确执行阶段，并且实际副作用只发生一次；若存在额外收尾请求，验证无可执行工具、次数有界且不突破取消或审批。
- 验证十次工具与多段进度/思考交替时，完成界面只有一个过程入口与一个最终结果区；展开能查看全部调用和正确顺序，收起不影响完整阅读。普通无工具回答不产生空过程入口。
- 验证进度、思考、工具载荷不进入结果复制、搜索和预览；最终建议与追问可以被复制和搜到。覆盖同文不同身份与重复事件，避免错误去重或重复显示。
- 验证工具失败、用户停止、预算耗尽、等待审批及恢复：既有有效结果保留、未完成事项直接可见，不伪造成功，不为收尾重放副作用。
- 用同一事件序列对照实时显示、结束事件和持久化后重载。覆盖切换 Session、断线恢复、显式替换事件及用户展开状态，结果不退化为末条确认。
- 验证历史缺少语义时不会触发模型/工具，不将不完整末段冒充完整交付，原始过程仍可查看。测试只使用脱敏合成数据，不复制真实个人对话。
- 新增回归须证明对应故障可使其失败，修复后连续运行 5 次通过。只使用隔离实例、临时数据库和本地模拟模型，不中断在用服务。
- UI 改动执行直接相关行为测试、适用 Svelte 检查与构建，完成隔离冷启动→首次打开→切换→服务中断恢复，并检查中英文、明暗、窄屏和键盘操作。交付前做对抗式审查，未执行的必需检查明确列出。
- 日常只运行直接受影响检查；全量 `pnpm verify:feature` 留给用户主动整体验收，不把未执行检查记为通过。

## Out of Scope

- 正文与工具节点交替展示、多张独立过程卡、将所有中间 text 展示或拼接为最终答案。
- 新增独立 AI 分类器、基于文本特征判断答案用途、无条件额外调用模型。
- 修改模型原始思考内容、记忆业务、工具权限或外部平台消息发送协议。
- 历史会话自动总结、批量改写、迁移或重跑真实工具。
- 重做 Agent 首页、设置或 Room 多 Agent 界面；部署或重启在用服务。

## Further Notes

- 本版取代此前关于“所有 text 永远作为正文”“思考必须独立入口”“多个过程 section 有意保留”的要求。旧实现和旧测试需按本版产品行为修正，不将该行为变化解释为数据丢失。
- 上一版关于成熟产品统一采用正文与工具交替展示的论断没有充分依据，不作为设计证据。本版是 Molibot 已确认的产品选择，不宣称复制某个产品所有版本的布局。
- 既有 Session 存储与 Personal Agent 体验要求仍有效；本版仅修订回答交付与过程展示。实施时更新设计规范、真实交付记录和受影响验收清单，不提前标记已完成。
- 工作区已有其它 agent 的修改，执行前核对实际差异，不覆盖或回退无关工作。本次文档修订不证明旧实现通过了新验收。

### 实施验收（2026-10-29）

- 已实现：修复无步骤消息空白；移除首次工具前文字自动视为答案的推断；思考、说明和工具按原顺序留在一个默认折叠过程区；结果提交不清除过程记录。
- 已实现：助手记录先标记 process，完成时提交 final 或 partial；只有过程的回合标记为 none。正常工具后模型请求收到单一完整交付规则，不增加模型轮次；SSE done 不以 token 或诊断补造答案。
- 61 项定向单元/集成测试连续 5 轮通过；3 个关键浏览器场景（冷启动与恢复、审批不执行、十次工具统一过程）连续 5 轮通过，共 15 次。思考、停止和未定稿显示的 3 个浏览器场景此前也连续 5 轮通过，并在最终版本再次 3/3 通过。普通消息空白、进度外露和 process-only 投影均有修复前失败证据。
- 根类型检查、Desktop Svelte 检查（0 错误/0 警告）、前后端构建及直接相关源码守卫通过。原有“思考自动外露”和“token 直接作为答案”的测试断言，已按本版明确行为调整。
- 未执行：真实 Provider、原生 App、全量回归、当前在用服务重启。历史记录不自动重写，旧记录缺失的完整答案不会被伪造。

- 时间线补充验收：三段思考、两次工具及其间进度按原顺序平铺，没有内层思考折叠卡，最终结果独立。该浏览器场景及相关思考/停止场景连续 5 轮通过（15/15）；39 项相关单元、3 项源码守卫、Desktop Svelte（0/0）与构建通过。已查看宽窗与深色窄窗截图。
