# Feature 开发验证自动化

日期：2026-10-12

文档状态：阶段 1 的浏览器部分、阶段 2 的验证基础设施、P0 浏览器场景与 P0 收尾细节（超时 UI 呈现、审批竞争/队列的集成用例、会话切换的存储回读、刷新接续阶段 1）已交付（2026-10-15）；刷新接续的逐字实时回放（阶段 2）与原生 App 测试未建设。测试接缝已与用户确认，仓库未配置 issue tracker，暂不发布 issue。覆盖清单见 [tests/ui/COVERAGE.md](../../tests/ui/COVERAGE.md)；当前状态与未验证项见 prd.md。

## Problem Statement

每个 feature 开发完成后，目前只能靠单元测试、类型检查、构建和人工走查来判断是否可以交付。历史返工反复出现同一类问题：首次打开空白、点击没反应、重启后配置丢失、审批后工具重复执行或没执行、会话之间状态串了、服务断开后界面永久加载。这些问题单元测试拦不住，人工走查又容易漏，而且依赖人记得去做。

开发 agent 宣称"已完成"时，缺少一个统一、可重复、不碰真实用户数据的方式来证明：界面真的能用、业务状态真的正确、副作用真的只发生了一次。现有初步尝试还暴露了几个隐患：测试进程继承了本机全部环境变量；原生 App 与真实 App 共用同一个应用标识，可能接管或读写真实数据；模型模拟只覆盖了最理想的回复形态；"该跑哪些测试"由 agent 自行判断。

## Solution

提供一套只在开发流程中运行的验证体系，核心是一个**隔离的 Molibot 实例**：临时数据目录、临时 HOME、空闲端口、独立应用标识，以及一个按用例预设回复的本地模型服务。除模型外，HTTP handler、Runner、工具、队列、审批、存储全部是真实代码。

测试从外部驱动这个实例：
- **浏览器 UI 测试**：用 Playwright 打开真实桌面前端，WebKit 为主（接近 macOS 的 WKWebView），Chromium 只跑冒烟。
- **原生 App 测试**：用 WebdriverIO 加 Tauri 内置驱动启动真实 App，只覆盖浏览器测不到的原生链路。
- **断言**：只看三处——界面反馈、HTTP API 返回的业务状态、磁盘或数据库里的实际结果。

现有 node:test 集成测试（真实 handler 加临时数据库）继续负责运行时细节，例如竞态窗口、恢复去重、幂等。UI 测试只验证这些行为在界面上的表现。

开发 agent 在 feature 完成后运行统一入口 `verify:feature`。入口根据本次改动的文件自动选择测试，失败则修复，通过后交付。环境不满足的检查明确标记为"未验证"，不算通过。不接入发布流程。

## User Stories

### 产品负责人

1. 作为 Molibot 所有者，我希望每个 feature 交付前都经过自动化的界面和业务验证，以便我不用自己逐项点一遍。
2. 作为 Molibot 所有者，我希望测试绝不读写我的真实数据目录、设置库、队列库和工作区，以便跑测试时我可以照常使用 Molibot。
3. 作为 Molibot 所有者，我希望我的 Molibot App 开着的时候也能跑原生测试，测试 App 不会把操作交给我正在用的实例，以便测试和日常使用互不干扰。
4. 作为 Molibot 所有者，我希望测试不会用我的 API Key 或渠道凭据去调用真实模型或真实渠道，以便不产生费用和对外消息。
5. 作为 Molibot 所有者，我希望交付说明清楚列出哪些检查通过了、哪些因环境缺失没有执行，以便我知道还剩哪些风险。
6. 作为 Molibot 所有者，我希望看到覆盖清单区分"已实现""待实现""环境受限"，以便我知道哪些功能真的有测试保护。
7. 作为 Molibot 所有者，我希望正式安装包里不含任何测试驱动，以便产品不暴露额外的自动化入口。
8. 作为 Molibot 所有者，我希望日常 feature 验证在几分钟内跑完，以便验证不会拖慢开发节奏。

### 开发 agent

9. 作为开发 agent，我希望用一个命令完成本次改动需要的全部验证，以便我不必记住每类改动要跑哪些测试。
10. 作为开发 agent，我希望验证入口根据改动的文件自动选测试，以便不会因为我判断失误而漏掉相关回归。
11. 作为开发 agent，我希望可以在自动选择的基础上手动追加测试，但不能删掉自动选中的部分，以便覆盖只增不减。
12. 作为开发 agent，我希望每次都会跑一组基础冒烟测试，以便任何改动都不会让启动和发送消息坏掉。
13. 作为开发 agent，我希望改到原生通信、启动、单实例或权限相关代码时，入口强制要求原生 App 测试，以便浏览器测不到的问题不会漏过。
14. 作为开发 agent，我希望测试失败时自动保留截图、操作轨迹、前后端日志、模型请求记录和运行事件，以便我不用复现就能定位原因。
15. 作为开发 agent，我希望验证命令只负责验证、不自动改代码，以便修复始终是有意识的改动。
16. 作为开发 agent，我希望新写的测试先连续跑多遍都通过才能收进测试集，以便尽早发现时好时坏的测试。
17. 作为开发 agent，我希望测试不靠固定等待时间判断成功，而是等待可观察的状态，以便测试既快又稳定。
18. 作为开发 agent，我希望测试不自动重试，以便第一次失败不会被掩盖。

### 测试编写者

19. 作为测试编写者，我希望每个用例能为模型服务登记自己的预设回复序列，以便测试控制指令不混进提示词。
20. 作为测试编写者，我希望模型服务能把工具调用参数拆成多段流式发送，以便覆盖真实模型分段输出时的参数拼接。
21. 作为测试编写者，我希望模型服务支持一次发起多个工具调用，以便覆盖并行工具调用。
22. 作为测试编写者，我希望模型服务能模拟流式中途报错、连接断开、HTTP 错误码和 429 限流，以便验证错误提示和恢复。
23. 作为测试编写者，我希望可以让模型回复暂停在某个点，由测试决定何时继续，以便稳定制造 Stop、队列、插话和审批竞争的时间窗口。
24. 作为测试编写者，我希望模型服务保存每个请求的完整内容（模型名、系统提示词、消息、工具列表），以便断言模型选择和提示词合并结果。
25. 作为测试编写者，我希望没有匹配到预设回复的请求被明确记录并让测试失败，除非用例声明允许，以便意外的额外请求不会被悄悄吞掉。
26. 作为测试编写者，我希望用例检查模型请求的总数，而不只是按标记筛选后的数量，以便发现重复执行。
27. 作为测试编写者，我希望页面报错和未处理的异常默认让测试失败，确实可忽略的单独列白名单，以便前端崩溃不会被当作通过。
28. 作为测试编写者，我希望聊天类用例在共享实例里各自新建会话，以便既快又互不依赖。
29. 作为测试编写者，我希望会改全局状态的用例（设置保存、服务重启、冷启动）每个都用独立实例，以便它们不污染其他用例。
30. 作为测试编写者，我希望优先用角色、名称和标签定位元素，只在没有可访问名称时才加测试 ID，以便测试同时督促界面的可访问性。
31. 作为测试编写者，我希望有一个统一的数据准备方式，从默认设置构造测试所需的 Agent、会话、文件和任务，以便不复制用户数据或凭据。
32. 作为测试编写者，我希望能从外部停止和重启隔离实例的服务，以便验证服务中断后的恢复。

### 被验证的行为（P0）

33. 作为用户，我希望首次打开 App 不会空白，输入框可以直接使用，启动弹窗可以处理。
34. 作为用户，我希望 Enter 发送、Shift+Enter 换行、空消息不发送、连点不会重复提交。
35. 作为用户，我希望首次发送和连续发送都能看到流式回复，回复完成后输入框恢复可用。
36. 作为用户，我希望请求超时、报错或断开时看到清楚的提示，并且可以再次发送。
37. 作为用户，我希望批准前工具绝不执行，批准后恰好执行一次，原任务继续完成。
38. 作为用户，我希望拒绝后工具不执行，等待状态结束，后续消息正常。
39. 作为用户，我希望重复点击审批、提交中切换会话、处理已过期审批时，不会重复执行也不会卡住。
40. 作为用户，我希望在生成中、工具执行中、待审批时都能停止，停止后可以继续发送。
41. 作为用户，我希望切换会话时消息、草稿、审批和运行状态不会串，后台回复归属到正确的会话。
42. 作为用户，我希望忙碌时发送的消息排队、按顺序执行，可以取消、清空和插话，恢复后不重复执行。
43. 作为用户，我希望有消息排队时出现审批，审批和队列都能正确推进。
44. 作为用户，我希望设置保存后离开再回来、重启服务后都能读回，且不覆盖其他配置。
45. 作为用户，我希望服务中断恢复后界面不会永久加载，也不会出现重复消息或重复执行。
46. 作为用户，我希望生成过程中刷新页面后能接上正在进行的回复，而不是丢失或重复。

### 原生链路（P0 原生部分）

47. 作为用户，我希望在 App 里流式回复和普通网页一样正常，因为 App 走的是原生网络通道。
48. 作为用户，我希望在 App 里下载或预览的文件内容完整，不会被悄悄截断。
49. 作为用户，我希望 App 自己拉起后台服务，令牌握手成功，并且服务崩溃后能自动恢复。

## Implementation Decisions

### 测试接缝

- **只设一个主接缝：隔离的 Molibot 实例。** 浏览器测试和原生测试都从外部驱动它，断言只读界面、HTTP API 和磁盘/数据库。不新增其他测试接缝。
- **模型是唯一的假依赖。** 模型服务说 OpenAI 兼容的 chat completions 协议，通过现有的自定义 Provider 配置接入，所以真实的 Provider 适配器和流解析都在被测范围内。
- 运行时细节继续由现有 node:test 集成测试负责（真实 handler 加临时数据库或可注入 store）。每条 P0 用例都标明由哪一层负责主要断言，见下方"P0 用例与负责层"。

### 隔离实例

- 组成：临时数据目录（固定前缀）、临时 HOME、空闲端口、预设回复模型服务（只监听本机回环地址）、外部渠道关闭。
- **环境变量白名单**：子进程只拿到运行必需的变量（PATH、Node 相关、临时 HOME 和数据目录、测试端口、关闭外部渠道的开关），不继承本机全部环境变量。API Key、渠道凭据、代理设置一律不透传。
- **启动前守卫**：数据目录不在固定临时前缀下、模型地址不是本机回环、解析出的任何存储路径落到真实数据目录时，拒绝启动并报错。守卫由隔离实例自己执行，不依赖用例自觉。
- **服务启动沿用 evals 的临时服务启动方式**，也就是走正式启动脚本，从而获得服务租约、信号处理和强制退出。但**数据准备不同**：evals 会复制所有者的 Provider 配置，UI 测试只从默认设置构造数据，绝不复制所有者的设置或凭据。
- **原生 App 隔离**：测试构建通过配置覆盖使用独立的应用标识。这样单实例锁、`app_data_dir`（导入主题、桌面偏好）都和真实 App 分开；同时传入临时 HOME 和数据目录，主题来源等基于 HOME 的路径也落在临时目录。测试构建里关闭开机自启和自动更新。
- 提供外部的服务停止和重启控制，用于恢复类用例；重启后数据目录不变。

### 预设回复模型服务

- 每个用例登记自己的回复脚本。脚本按条件匹配请求，例如最后一条用户消息的内容、是否已带工具结果、是否带工具列表；匹配后返回预设的回复步骤。不使用嵌在消息里的控制标记。
- 回复步骤支持：文本分段流式发送；工具调用参数分段流式发送；同一轮多个工具调用；暂停等待测试释放；流式中途报错；断开连接；HTTP 错误码（含 429）；非流式回复。
- 每个请求都完整记录模型名、系统提示词、消息、工具列表和匹配结果。
- 没有匹配的请求记为"未匹配"并让用例失败。后台请求（例如标题生成）需要由用例或共享数据准备显式声明允许。
- 只覆盖 OpenAI 兼容协议，其他协议在覆盖清单里明确标为"未覆盖"。

### 驱动

- **浏览器**：Playwright，以 WebKit 为主跑全部场景，Chromium 只跑冒烟。不同时引入其他 UI 框架。
- **原生**：WebdriverIO 加 Tauri 内置驱动插件。插件只在一个默认关闭的 Cargo 编译开关下编译，正式构建不开启；另加一项检查确认正式构建产物里没有驱动。WebdriverIO 相关依赖放在桌面 App 包内，等阶段 1 的原生可行性验证通过后再加入。
- **原生测试只覆盖浏览器测不到的链路**，控制在 3–5 条：原生网络通道下的流式回复；二进制下载完整性；Supervisor 用指定数据目录拉起服务并完成令牌握手；按应用标识的单实例行为；服务崩溃后自动恢复；冷启动窗口可用。其余行为全部交给浏览器测试。

### 防假通过的统一规则

- 关键用例同时断言三层：界面反馈、业务状态（HTTP API 或存储回读）、实际结果（文件内容、执行次数、模型请求总数）。
- 只等待可观察状态，不用固定等待时间判断成功。
- 重试次数为 0。
- 页面报错和未处理的 Promise 拒绝默认让用例失败，例外走显式白名单。
- 模型请求断言用总数，不用筛选后的子集。
- 新用例收进测试集前，必须连续重复跑 5 次全部通过；并在评审时证明它能被对应的故障弄失败（例如注释掉被测的守卫后，用例应当失败）。
- 用模拟模型的用例和用真实 Provider 的用例分别打标签，真实 Provider 用例不进入日常验证。
- 不为测试增加"直接批准""跳过权限""伪造任务成功"之类的业务分支。

### 用例隔离粒度

- 聊天类用例：同一个测试进程共用一个隔离实例，每个用例新建自己的会话和数据。
- 改全局状态的用例（设置保存、服务重启、冷启动、恢复）：放在单独的分组，每个用例启动独立实例。

### 稳定定位

- 优先用角色、可访问名称和标签。只有元素确实没有可访问名称时才加测试 ID，测试 ID 不改变业务行为。

### 执行入口与自动选择

- `verify:feature`：类型检查，加按改动选中的逻辑/API 测试，加基础冒烟，加按改动选中的 UI 场景，必要时加原生测试。
- `test:ui`：浏览器里的完整 UI 测试。
- `test:app`：原生 App 核心测试。
- `evals`：保持不变。
- **自动选择是确定的**：维护一份"改动路径 → 测试标签"的映射，由 `verify:feature` 根据 git 改动计算。基础冒烟每次都跑。映射的初始规则：
  - 桌面聊天界面 → 聊天、审批、会话标签
  - Agent 运行时、队列、审批、会话推进、流式路由 → 完整核心回归
  - 设置相关界面和设置存储 → 设置标签，加 round-trip 集成测试
  - Tauri 原生代码、桌面 API 传输层、Supervisor、启动和握手 → 必须跑原生测试
  - 没有命中任何规则的改动 → 基础冒烟，加完整核心回归
- agent 可以追加标签，不能删掉映射选中的部分。
- 原生测试环境缺失时，入口输出"原生：未验证"及原因，交付说明必须照实列出，不能当作通过。
- 时间预算：`verify:feature` 默认选择的范围应在 5 分钟内跑完，超出就拆分或下沉到集成测试层。

### 失败证据

- 失败时附上截图、Playwright 操作轨迹、服务和前端日志、模型请求记录（完整请求体）、页面报错列表，以及本用例对应的运行事件。证据收集由测试工具统一完成，用例不需要单独处理。

### P0 用例与负责层

| 场景 | 主要断言所在层 | UI 层验证 |
|---|---|---|
| 冷启动 | 浏览器加原生 | 首屏非空、输入框可用、启动弹窗可处理 |
| 消息输入 | 单元（含输入法组合事件） | Enter、Shift+Enter、空消息、连点不重复 |
| 消息回复 | 浏览器 | 首发、连发、流式更新、输入恢复、请求总数 |
| 请求失败 | 浏览器 | 超时、错误码、断开、429 的提示，以及再次发送 |
| 允许审批 | 浏览器 | 批准前无文件、批准后文件正确、工具恰好一次、原任务完成 |
| 拒绝审批 | 浏览器 | 无文件、等待结束、后续消息正常 |
| 审批竞争 | 集成（延迟审批响应制造窗口） | 重复点击、提交中切换会话各 1 条 |
| Stop | 集成（运行屏障）加浏览器 | 生成中、工具中、待审批时停止，之后再发送 |
| 会话切换 | 浏览器加存储回读 | 草稿、审批、状态不串，后台回复归属正确 |
| 队列与插话 | 集成（执行次数、去重）加浏览器 | 入队、顺序、取消、清空、插话 |
| 排队时审批 | 集成加浏览器 | 审批和队列都正确推进 |
| 设置保存 | 集成（整对象 round-trip）加浏览器 | 保存、离开返回、重启回读、不覆盖其他配置 |
| 服务恢复 | 浏览器加原生 | 停启服务后无永久加载、无重复消息或执行 |
| 刷新接续 | 浏览器 | 生成中刷新页面后接上回复，无丢失无重复 |
| 原生传输 | 原生 | 流式回复、二进制下载完整、握手、崩溃恢复 |

### P1 待覆盖清单（随相关 feature 补齐）

会话管理（新建、重命名、搜索、筛选、归档、恢复、删除、批量）；忙碌保护（运行中或待审批时拒绝删除和归档）；Agent（创建、编辑、切换、默认、头像、角色文件、归属）；Room（成员、多对话隔离、草稿、执行归属）；计划（只覆盖已实现入口）；导航（展开折叠、右键菜单、切换、返回、选中态）；模型与 Provider（配置、选择、能力过滤、请求使用正确模型，靠完整请求记录断言）；Prompt/Skill（最终合并顺序、路由、临时控制不进入持久化历史）；附件；文件与产物；记忆；提醒和周期任务（可控时间加真实事件系统）；MCP（本地 MCP 服务）；MCP OAuth（本地授权服务）；插件与子代理；Mini App；图片和音频（本地媒体服务）；Trace；中英、明暗、窄宽度与固定保存栏。

## Testing Decisions

- **什么是好测试**：只验证外部可观察的行为，也就是用户看到的界面、API 返回的状态、落盘的结果；不断言内部函数调用、组件内部状态或具体实现路径。实现重构后行为不变，测试就不应该失败。
- **测试基础设施本身也要测**：
  - 隔离实例的守卫：非临时目录、非回环模型地址、存储路径落到真实目录时拒绝启动；子进程环境里不出现白名单以外的变量。
  - 预设回复模型服务：分段工具调用能被真实 Provider 适配器正确拼回；未匹配请求会被记录并导致失败；暂停和释放可控。
  - 自动选择映射：给定改动路径集合，输出预期的标签集合；原生相关路径一定选中原生测试。
  - 正式构建检查：产物中不含测试驱动。
- **被测模块**：隔离实例、预设回复模型服务、自动选择映射，以及通过浏览器和原生驱动验证的桌面前端、HTTP API、Runner、工具、队列、审批、设置存储、Supervisor、原生网络通道。
- **可参考的现有测试**：
  - evals 的临时服务启动方式：数据目录隔离、服务租约、强制关闭外部渠道。
  - 桌面 API 系列 handler 测试：真实 handler 加临时数据。
  - 服务启动与租约测试：端口、租约、崩溃报告、数据目录作用域、服务归属。
  - 设置字段的整对象 round-trip 回归：保存、新建 store、读回。
  - Pi 恢复与 Room 审查的真实运行时端到端测试：真实重启、审批前不重发、批准恰好重发一次。
  - Playwright 原型：worker 级隔离实例和失败证据附件，可作为起点，按本文决策修正。
