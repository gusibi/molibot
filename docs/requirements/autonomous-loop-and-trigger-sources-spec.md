# 任务看板与 Agent／Team 自主执行 Spec

日期：2026-11-05。阶段：产品方案已确认，尚未实施。本文描述拟议行为，不代表能力已经交付。

## 1. 目标与范围

用户手动创建一张 Todo，指定单个 Agent 或 Agent Team，启动后由执行者持续推进。Team 的负责人根据结果安排成员串行协作，例如方案 → 编码 → CR → 修改 → 复核；任务满足完成条件后进入 Done。用户从同一个看板管理任务、处理阻塞、查看进度和领取成果。

参考 [agent-autoloop](https://github.com/KKKKhazix/agent-autoloop) 的回执驱动、等待释放资源、复查唤醒和事件因果链约束。机制内置共享运行时，不引入其进程外编排器，不让插件控制执行循环。这里的持续推进包括执行、等待和再次唤醒，不要求模型或进程一直运行。

### 第一版交付

- 将现有计划页升级为统一任务看板，采用 Todo／Doing／Done 三列，保留现有视觉体系和详情工作区。
- 手动创建、手动启动任务；支持单 Agent 或负责人动态派活的串行 Team。
- 完成条件、成果、协作记录、审批、暂停恢复、配置修订、累计预算与交接上限。
- 旧计划无损纳入看板，保留原执行者、验收规则、历史与恢复语义。

### 不在第一版范围

- GitHub、飞书多维表格等 trigger 插件、来源轮询、AI 分流和触发源管理。
- 定时自动创建任务、从聊天自动声明任务、新增聊天声明工具；现有定时任务保持原执行方式。
- 多成员并行、工作项 DAG、固定流程编辑器、独立 Team 模板管理器。
- 运行中实时改目标、跨任务自动派生与复杂依赖调度。
- 强制工作项分解、规模化批量验收、代码发布或合并流水线。

后续 trigger 插件应通过共享创建入口提交任务并选择获授权的 Agent／Team，不另建执行循环。本版只保证手动创建链路完整，不实现第三方来源协议。

## 2. 领域与既有能力边界

术语定义维护在[领域词典](../reference/CONTEXT.md)。

| 对象 | 职责 |
| --- | --- |
| 看板任务（Kanban Task） | 用户目标、完成条件、执行配置、状态、预算、成果和历史的稳定工作单元 |
| Agent | 单个执行者，可用多轮推进同一任务 |
| Team Coordinator | 明确指定的团队负责人，选择成员、组织交接、汇总成果并发起任务结案 |
| Team 成员 | 按负责人分配完成本次工作，提交结果与证据 |
| 执行轮次 | 一次有界执行，不等于任务本身，也不等于成员交接 |
| 成员交接 | 实际推进责任从一个执行成员转给另一成员，包括 CR 后返回修改 |
| Runtime Task | 既有定时／提醒 CRUD 对象；其 todo 类型不是本看板 Todo |

当前 Agent Team 的底层是 Agent Room。Primary Agent 只决定默认消息接收者，不自动拥有团队负责人的职责。当前多人 discussion 为只读，既有队列也不会根据结果自动组织方案、编码、CR 和返工。团队负责人、可写成员的串行派活、整体完成判断和持久化等待释放资源均属于本版需要补齐的能力。

看板任务复用、扩展既有 Durable 聚合的目标身份、版本、租约、预算和恢复基础；单 Agent 与 Team 是执行方式。计划结构是可选任务内容，不要求新任务先生成完整步骤计划。旧计划仍由其原路径执行。不得为 Team 建立第二套独立的目标状态、预算或审批真相来源。

## 3. 创建与启动

创建表单：

- 目标必填；标题可从目标生成并编辑。
- 完成条件可填；未填时，由单 Agent 或 Team 负责人在启动阶段生成可见条件，再开展实质工作。没有有效条件时等待用户补充，不能直接执行并自行宣称完成。
- 选择单 Agent，或选择已有 Team 并明确指定负责人；负责人须在成员中，不把 Primary Agent 隐式当作负责人。
- 可选所属 Project。执行使用项目目录；无项目时须有明确工作目录，不从当前打开的聊天推断。
- 展示并允许设置任务累计预算、成员交接上限、审批策略和是否需要人工验收。

创建后留在 Todo，不产生业务执行或自动派活。点击“开始”或拖入 Doing 才提交启动；配置不完整或服务拒绝时卡片留在原列并说明原因。启动动作幂等，重复点击不重复运行。

启动时保存目标版本、执行者、成员、负责人、分工、工作目录和预算配置。每个任务拥有独立的成员上下文，不回灌日常 Room 聊天，也不依赖源房间当前打开状态。后台执行上下文不作为普通会话混入列表。

房间成员或分工后续变化不自动修改已启动任务。用户可暂停后显式更新任务配置；禁用、删除 Agent 或撤销权限仍立即阻止后续不获授权的执行，配置快照不冻结安全授权。

## 4. 看板与进度

统一看板支持搜索、Project、执行者和状态筛选。所有筛选和计数以完整任务集合为依据，不能只筛当前分页。

| 列／范围 | 进入条件 | 子状态示例 |
| --- | --- | --- |
| Todo | 已创建但未启动 | 待启动、配置待补齐 |
| Doing | 已启动但尚未满足完成条件 | 排队、执行、验证、等待审批、等待用户、等待复查、等待重试、暂停、异常、预算／交接超限、恢复审核、待验收 |
| Done | 完成条件全部通过，且要求的人工验收已通过 | 已完成 |
| 归档 | 已取消 | 已取消 |

Doing 是产品阶段，不意味着正在占用执行资源。失败或部分完成的任务仍可在 Doing 显示“已停止”，但资源占用、运行数和自动恢复必须读取真实运行状态，不能依据看板列判断。

卡片展示标题、来源、执行者／Team、当前推进成员、最新事实进展、等待原因和更新时间。轮次、累计预算和交接计数在详情展示；不凭模型推测生成进度百分比。有明确工作项时才展示完成数量。

拖入 Doing 等同启动；不能通过拖入 Done 绕过完成检查。任务从创建到交付始终是一张主卡片，成员交接不生成顶层任务。窄窗使用流内单列详情与返回入口，遵循 [DESIGN.md](../../DESIGN.md)。

### 详情工作区

- **概览**：目标、完成条件、所属项目、执行配置、当前事实、下一步和待处理操作。
- **协作记录**：成员接收工作、交付、CR 退回原因、复核、等待、重试、配置修订与恢复，能展开查看相应执行证据。
- **成果**：阶段与最终结论、完成条件核对、文件／报告／代码修改或外部证据引用、未验证项。

界面优先回答“做到哪里、为什么停、下一步是什么”，完整对话和工具调用折叠为执行细节。文件复用现有预览能力，不新增独立成果中心。首页保留待处理与成果入口，链接到同一任务详情；看过或收起成果不删除任务历史。

## 5. 单 Agent 与 Team 执行

### 单 Agent

在任务专属上下文内按回执推进、等待或复查。自然结束一轮不等于完成任务；缺少有效后续意图或完成证据时进入待用户确认，不隐式无限续跑。

### Team

负责人动态选择下一位成员，提供本次目标、输入、完成要求与已有成果。第一版任务内串行执行，协调调用也计入预算，不与成员并发开展业务。成员结果交回负责人，由负责人决定交给下一成员、退回修改、复查、询问或申请结案。

负责人作为实际业务执行者工作时也须遵守成员执行规则。协调调度与实际工作分开计数，不能把任意业务工作标为“调度”来逃避护栏。

例如：设计交付方案 → 编码交付修改 → CR 提出问题 → 编码修复 → CR 通过 → 负责人核对完成条件并汇总交付。CR 发现问题属于正常协作，不算系统故障。

整个任务只允许一个有效推进者和一个有效配置版本。任务内串行不等于 Project 全局写互斥；仍使用既有工作目录权限与冲突保护，不能声称不同任务共享目录时天然隔离。

## 6. 结构化回执与可靠提交

回执绑定任务、执行轮次与当前配置版本。执行者可提交本轮结论、证据、交接／继续推进、提问、通知、关闭已解决问题、预约或取消复查、申请完成。动作可组合，例如交付阶段结果并预约复查；同一阻塞的未关闭问题不重复创建。

运行时确定性校验权限、当前任务状态、预算和交接上限。有效回执的执行结算、已消费输入、预算、任务状态和下一次唤醒须可靠关联：优先在现有聚合事务内提交状态与持久化 wakeup，提交后才派发。重复提交只生效一次；相同回执身份但内容冲突须拒绝，旧版本结果不能覆盖新状态。

回执缺失或格式错误不重做已完成业务；保留产物和执行结果，显示协议异常，等待安全修正或用户处理。成员完成不自动把主任务设为 Done。

定时复查复用 runtime 事件／内部唤醒基础，补跑与超窗遵循既有恢复约束，不写系统调度器。提问回答、审批决定与到期复查均回到原任务，不重置预算或交接计数。

## 7. 完成条件与成果

新任务默认自动验收。单 Agent 或 Team 负责人提出完成申请，附完成条件逐项核对和证据；可确定检查的条件必须通过检查，缺少证据、仍有必需工作或运行状态不确定时不得进入 Done。

选择人工验收的任务先留在 Doing／待验收，用户确认后才进入 Done。用户退回时记录原因并继续推进，不覆盖旧成果。普通启动默认不额外要求确认模型补充的完成条件，但用户可查看，并可按修订规则调整；生成的条件不得缩小用户目标来制造完成。

最终交付至少包括结论、完成条件核对、产物或证据引用以及未验证项。没有文件的任务可以交付有证据的处理结论。失败、超限或取消也保留阶段成果、未完成项与原因，不能因未成功而隐藏产物。

## 8. 预算、交接与失败

### 三类计数

- **执行轮次**：同一成员内部继续、等待恢复和模型执行的有界记录，独立于成员交接。
- **成员交接**：默认最多 8 次。首次分配不计；实际工作从 A 转给 B 加一，B 返回 A 再加一。负责人纯调度不计，协调调用用量照常计费。相同成员内部续轮、失败重试、回答和复查不增加交接次数。
- **事件因果深度**：未来跨任务派生事件的约束，不用成员身份是否变化代替判断；本版不开放跨任务派生，不把它与成员交接或模型轮次混为一谈。

### 累计预算

任务累计预算与每轮运行预算同时生效。所有模型调用，包括负责人调度、成员、辅助调用、压缩和失败重试均计入；切换执行者、换上下文、暂停恢复或收到回答不清零。用量缺失不得当作零，须显示统计缺口并阻止无界自动推进。

启动前展示具体累计 token 上限与单轮限制，采用现有预算配置的有界默认值；默认数值须在实现配置和验收中明确，不能把缺省解释为无限。每次新模型调用前检查额度，结算后再次检查；若无法严格限制单次请求的超额，必须在 UI 说明边界，不承诺精确费用硬上限。

下一次交接将超过上限，或累计预算耗尽时，停止派发并在 Doing 显示原因、计数和阶段成果。用户显式增加相应额度后才能继续；追加保留记录，不清零原账本、不自动结案。

### 失败与重试

仅对已确认未执行，或幂等／可查询确认可安全重试的临时故障进行退避重试。一次执行初次失败后最多自动重试 3 次，全部计入预算，下一次重试时间可见；进程重启不得重置重试次数。

审批拒绝、成员不可用、预算／交接超限、不可恢复配置错误、结果不确定的副作用不得作为临时故障盲目重试。失败到上限保留 Doing／已停止异常；恢复前先解决原因。CR 返工按正常交接处理，不计入这 3 次故障重试。

## 9. 审批、暂停与修订

### 审批与业务决策

新手动任务可选 deny／suspend，默认 suspend。旧无人值守任务默认拒绝策略保持不变，不用新默认值覆盖旧设置。

业务拍板与工具权限审批分开保存。卡片在详情中提供明确问题、影响和可选操作；工具审批必须绑定请求、执行身份、范围与参数。拒绝仅禁止该操作，拒绝结果交回执行者后可以寻找已获授权的替代方案；没有可行方案时保持阻塞，不循环申请同一被拒操作。

等待时释放 runner、执行租约与连接，不产生模型调用；通知和界面轮询不调用模型。批准、拒绝、过期、取消、重启及重复点击必须有明确结果和唯一消费方。工具授权过期不得视为批准，任务保留可处理状态。审批恢复沿原任务和已确认成果继续，不要求所有路径保留原 runId；普通审批和 Durable attempt 的不同恢复方式由共享层适配。

原生等待审批能力必须验证真实释放资源，不能直接沿用 Room 当前无限 inline wait。任务关闭或权限撤销后，迟到批准不能启动执行。

### 暂停、恢复与取消

暂停先停止后续派活，再请求当前 Agent 在安全边界停止。期间显示“正在暂停”；当前工具确认结束或其不确定结果已记录、且写入者已停止后，才显示“已暂停”。不确定副作用进入恢复审核，不自动重放。

恢复从已确认成果和安全恢复点继续，不能重跑整个任务。取消同样区分请求中与已停止，停止后归档并保留成果；迟到回执或唤醒不能复活已取消任务。

### 用户介入

执行中可回答问题、补充资料。新资料可靠接收并由后续执行消费，不在第一版实现实时 steer 改目标。

目标、完成条件、执行者、Team 分工、目录与预算等关键修订须先暂停，保存版本和修订记录。恢复前由负责人或新的单 Agent 核对旧成果，保留已发生副作用，不把新配置应用于旧的已认领执行。更换执行者不自动授予原执行者拥有的权限。

旧计划继续使用原有修订和执行者绑定限制，不因新任务允许更换执行者而放开旧绑定。

## 10. 持久化、重启与旧计划纳入

任务状态由共享执行聚合持有，协作记录和 UI 是投影。临时运行控制不写普通会话消息；结构化排障事件不回灌模型。修改 settings 字段时遵循整对象持久化 round-trip 守卫。

租约、状态版本、回执去重、预算和下一次唤醒覆盖进程崩溃窗口。重启后安全可确认的等待或排队工作按规则恢复；执行结果未知时进入恢复审核，不默认重新执行写操作。服务恢复后，审批、计数、成果和任务详情均能从持久化状态重建。

### 原计划投影

| 原始 execution.status | 看板 |
| --- | --- |
| planned | Todo |
| queued、running、verifying | Doing，保留排队／执行／验证子状态 |
| waiting_for_user、waiting_for_approval | Doing，保留决策／验收／审批类型 |
| paused、recovery_required | Doing，保留暂停／恢复审核 |
| partial、failed | Doing，明确已停止且不会自动运行 |
| completed | Done |
| cancelled | 归档 |

现有 planStatus 将 completed 映为 archived，其 archived 标志不能直接作为新看板过滤条件；原始状态与看板阶段须分开。完成后的 Done 不等于用户归档。

保留旧计划 ID、原 Agent 绑定、输入与证据、修订历史、首次批准与权限选择、人工验收、返工、恢复审核、删除限制和跨 Session 查找。不得把旧的用户确认验收自动改为新任务默认自动验收，不因已完成被旧投影标为 archived 而丢失卡片。

持久化扩展采用兼容读取与必要的加法 schema 升级，保持旧记录原语义；实施前为实际存储变更明确备份、升级和失败恢复方案。不自动重写旧目标、迁移旧 Agent 绑定或将旧计划改为 Team。源 Room 不是任务成果和运行状态的真相来源。

## 11. 验收与验证

测试使用临时数据库、隔离目录、本地模拟模型，不调用真实账号、不修改用户服务。

1. **创建与启动**：创建后留 Todo，不调用模型；重复启动只产生一个有效执行；单 Agent 和 Team 均可真实进入 Doing。
2. **团队闭环**：真实共享入口与 Runner，模拟方案 → 编码 → CR 退回 → 编码修改 → CR 通过；只有一个主任务，成员串行，完成后 Done 且可读成果。
3. **护栏**：首次派活不计交接；第 8 次允许、第 9 次被阻止；负责人调度、重试与压缩计预算；换成员和回答不清零；超限只在显式追加后继续。
4. **回执与崩溃**：重复提交、版本冲突、状态提交与派发之间重启、重复唤醒；不丢后续工作、不重复确认成果、不重放未知副作用。
5. **等待与审批**：业务问题、Broker、Host Bash、批准／拒绝／过期／迟到决定、重启后回答；等待期间无模型调用且释放实际 runner 资源，拒绝不升级权限。
6. **暂停与配置**：暂停请求中不伪报已暂停；停止后恢复不重做成果；目标／执行者变更有版本；修改源 Team 不改已启动任务，权限撤销立即生效。
7. **失败**：仅安全故障最多自动重试 3 次，退避和计数持久化；CR 返工不是故障重试；未知效果转恢复审核。
8. **验收与成果**：补齐条件后才开展工作；检查失败或证据不足不进 Done；可选人工验收；失败／取消仍可查阶段成果。
9. **旧计划**：临时库升级／重新打开后 ID、绑定、验收、证据和修订保持；所有状态映射正确，旧 completed 可在 Done 找到。
10. **桌面**：任务创建、筛选、详情、成果预览和拖动语义；改动包 svelte-check 无新增问题。隔离实例冷启动，首次打开／点击、页面切换、断连恢复后状态与可操作性正确。

若改动 settings，增加 save → 新建 store → load 全字段整对象回归。涉及 Tauri capability、CSP、HTTP scope 或原生命令时，运行相关原生用例并执行 Rust 重建。完整 verify:feature、完整 Playwright 和完整原生套件由用户在整体验收／发版前执行，不以单元测试替代定向集成和冷路径走查。
