# 任务看板与 Agent／Team 自主执行 Spec

日期：2026-11-05，2026-11-07 修订（自动开始、对话式详情、进度清单、流程来源、同项目串行）并于同日交付第一阶段（看板、创建、执行循环、护栏与 Desktop UI；第二阶段起的 trigger 来源插件未开始）。实际状态以[能力矩阵](personal-assistant-capability-matrix.md)为准。术语见[领域词典](../reference/CONTEXT.md)。

## Problem Statement

我有一类工作需要持续交给 AI 推进，而不是逐条在对话里催：

- **项目维护**：GitHub 项目遇到问题记录下来后，希望 AI 自动分析、设计方案、编码、Review，有问题打回修改，多轮 Review 后交付。单个 Agent 做不了，需要方案、编码、CR 等角色协作。
- **网站优化**：定期获取 SEO／GEO 数据，分析效果，改进并发布。
- **内容运营**：每天调研热点与数据，改写成自己的图文内容，准备小红书／公众号草稿。

现状无法支撑这些场景：

- 计划页只承接会话里生成的线性计划，要先批准步骤、绑定会话，不能直接“交给某个 Agent 或 Team 做完”，也没有 Todo／Doing／Done 的看板视图。
- Agent Team（Agent Room）只是多人对话：多成员 `@` 为只读讨论，Primary Agent 只是默认接收者，没有负责人按结果组织“方案 → 编码 → CR → 返工”的串行协作，等待审批时也不释放资源。
- 现有定时任务（Runtime Task）只能周期性发一条消息，不是可跟踪到完成的工作单元。
- 长任务执行时，我看不到“做到哪一步、为什么停、下一步是什么”，也没有统一的成果交付位置。
- 任务来源分散在 GitHub Issue、飞书表格、Google 表格，缺少统一的待办入口让执行器只盯一个地方。

## Solution

把计划页升级为统一任务看板：我创建一张 Todo，选择单个 Agent 或某个 Agent Team，以及所属 Project；执行器发现新任务后自动开始，像我在对话里发出这条消息一样推进，只是无人值守。

- **看板**：Todo／Doing／Done 三列，加一个默认收起的“已取消”区域。旧计划无损出现在看板上。
- **执行**：单 Agent 任务就像单 Agent 对话；Team 任务由负责人（默认是 Team 的 Primary Agent）按流程串行派活给成员，CR 打回属于正常协作。执行包括运行、等待和再次唤醒，等待期间不占资源、不调模型。
- **流程**：不做流程编辑器。流程来自现有的提示词合成：Project 的 AGENTS.md，没有就用全局与 Agent 规则；Team 按负责人的规则推进。流程里没写，执行者自行规划。关闭 Issue、提 PR、发布等步骤也由我写在流程中控制。
- **详情**：主区就是对话窗口，显示上下文、模型回复、工具调用、审批和成员交接，我可以在里面回答问题；右侧是进度面板，长任务显示 Agent 自己维护的勾选清单（任务一、二、三……做完一项勾一项），简单任务直接完成。
- **护栏**：完成条件、累计预算、成员交接上限、失败重试上限、审批挂起、暂停恢复、同 Project 串行。
- **来源**：执行器只消费看板 Todo。第一版只支持手动创建；后续 GitHub Issue、飞书、Google 表格等插件只负责把外部条目转成 Todo，以及按需回写状态，不参与执行。

机制参考 [agent-autoloop](https://github.com/KKKKhazix/agent-autoloop) 的回执驱动、等待释放资源、复查唤醒和事件因果链约束，但内置在共享运行时中，不引入进程外编排器，不让插件控制执行循环。

## User Stories

### 看板与创建

1. 作为用户，我希望计划页变成 Todo／Doing／Done 三列的任务看板，以便一眼看到所有交出去的工作处于哪个阶段。
2. 作为用户，我希望已取消的任务收在默认折叠的区域里，以便看板只显示需要关注的工作，又能找回取消的任务和它的成果。
3. 作为用户，我希望删除是一个独立操作而不是看板列，以便取消（保留成果）和删除（移除记录）不会混淆。
4. 作为用户，我希望只填一个目标就能创建任务，标题可由目标生成并可编辑，以便快速记录想交出去的事。
5. 作为用户，我希望创建时选择单个 Agent 或一个已有 Team，以便简单任务交给一个 Agent，复杂任务交给团队。
6. 作为用户，我希望选择 Team 时负责人默认是 Team 的 Primary Agent，也可以改成其他成员，以便不必每次重复指定，又能按任务调整。
7. 作为用户，我希望选择所属 Project，以便任务在项目目录里按项目规则、Skills、Memory 和权限执行。
8. 作为用户，我希望不选 Project 时必须给出明确工作目录，以便任务不会从我当前打开的聊天里猜测目录。
9. 作为用户，我希望可以填写完成条件，不填时由执行者先生成可见的完成条件再开工，以便任务有明确的“做完”标准。
10. 作为用户，我希望创建时看到并可调整累计预算、成员交接上限、审批策略和是否需要人工验收，以便控制成本和风险。
11. 作为用户，我希望有“自动开始”开关且手动创建时默认开启，以便创建完任务就自动执行，不想马上执行时可以关掉。
12. 作为用户，我希望关闭自动开始的任务留在 Todo，点击“开始”或拖进 Doing 才执行，以便我先攒任务再决定何时启动。
13. 作为用户，我希望配置不完整或服务拒绝启动时卡片留在 Todo 并说明原因，以便我知道要补什么。
14. 作为用户，我希望重复点击开始或重复唤醒都只产生一次执行，以便不会意外跑两遍。
15. 作为用户，我希望不能靠把卡片拖进 Done 绕过完成检查，以便 Done 永远代表真正完成。
16. 作为用户，我希望按关键字、Project、执行者和状态筛选，且计数基于全部任务而非当前页，以便筛选结果可信。
17. 作为用户，我希望卡片显示标题、来源、执行者／Team、当前推进成员、最新进展、等待原因和更新时间，以便不打开详情就能判断是否需要我介入。
18. 作为用户，我希望有进度清单的卡片显示已勾选数／总数，且不显示模型猜测的百分比，以便进度有事实依据。
19. 作为用户，我希望一个任务从创建到交付始终是一张卡片，成员交接不生成新卡片，以便看板不被内部协作淹没。
20. 作为用户，我希望窄窗下详情改为单列并有返回入口，以便小窗口也能使用。

### 详情与进度

21. 作为用户，我希望任务详情主区就是对话窗口，显示上下文、模型回复、工具调用和审批，以便执行过程和我平时对话看起来一样。
22. 作为用户，我希望 Team 任务的对话里标明每段是哪个成员说的、何时发生交接，以便看懂协作经过。
23. 作为用户，我希望在详情对话里回答执行者的问题、补充资料和处理审批，以便不必去别处找入口。
24. 作为用户，我希望我补充的资料被可靠接收并在后续执行中使用，而不是实时改掉正在执行的目标，以便执行稳定可预期。
25. 作为用户，我希望任务的执行对话不出现在普通会话列表里，以便日常聊天不被后台任务淹没。
26. 作为用户，我希望右侧进度面板显示进度清单、完成条件、当前推进成员、下一步或等待原因、预算与交接计数和成果入口，以便快速知道做到哪里、为什么停、下一步是什么。
27. 作为用户，我希望长任务由执行者拆成勾选清单，完成一项勾一项，可随执行调整，以便长任务的推进过程可见。
28. 作为用户，我希望简单任务不出现清单、做完直接结案，以便简单的事不被复杂流程拖累。
29. 作为用户，我希望清单全部勾选不等于任务完成，仍要通过完成条件，以便清单不会被用来制造完成。
30. 作为用户，我希望服务重启后进度清单、对话和面板都能恢复，以便不丢进度。
31. 作为用户，我希望成果区展示结论、完成条件核对、文件／报告／代码修改或外部证据引用和未验证项，文件复用现有预览，以便在一个地方领取交付。
32. 作为用户，我希望首页的待处理与成果入口链接到同一任务详情，看过或收起成果不删除历史，以便首页和看板一致。

### 流程与执行

33. 作为用户，我希望 Project 任务按项目里的 AGENTS.md（或 AGENT.md、CLAUDE.md）执行，没有时用全局与 Agent 规则，以便自动执行和我手动对话遵守同一套规则。
34. 作为用户，我希望 Team 任务按负责人的规则作为协作流程，成员做自己的部分时用各自规则，以便流程写在一处，角色各司其职。
35. 作为用户，我希望规则里没有流程时执行者自行规划，以便没写流程的任务也能推进。
36. 作为用户，我希望在流程中写“处理完关闭 Issue”“提交 PR”“发布草稿”等步骤，执行者用已授权工具完成并照常走审批，以便发布和回写由我的流程控制，权限不会因写进流程而放宽。
37. 作为用户，我希望单 Agent 任务在任务专属上下文中多轮推进，一轮自然结束不等于任务完成，以便长任务不会半途被当作完成。
38. 作为用户，我希望执行者没有明确后续意图或完成证据时转为等我确认，而不是无限续跑，以便不会空耗预算。
39. 作为用户，我希望 Team 负责人把目标、输入、完成要求和已有成果交给下一位成员，成员结果交回负责人决定下一步，以便协作有序。
40. 作为用户，我希望 Team 任务内成员串行工作，负责人协调不与成员并发干活，以便不会互相覆盖。
41. 作为用户，我希望 CR 发现问题打回修改被视为正常协作而非故障，以便返工不触发故障重试。
42. 作为用户，我希望每个任务对每个成员有独立上下文，不回灌日常 Room 聊天，也不依赖源 Room 是否打开，以便任务与日常对话互不污染。
43. 作为用户，我希望 Team 成员或分工后来变化不影响已启动的任务，以便执行中途配置不被意外改动。
44. 作为用户，我希望禁用、删除 Agent 或撤销权限立即阻止后续未授权执行，以便安全收回权限不必等任务结束。
45. 作为用户，我希望同一 Project 的任务按创建顺序串行，前一个完成或取消后才开始下一个，以便多个任务不会同时改同一个仓库。
46. 作为用户，我希望前一个任务在等待、暂停或失败停下时，后续同项目任务继续排队并显示在等谁，以便知道为什么没开始，并可通过处理或取消前一个任务放行。
47. 作为用户，我希望不同 Project 的任务可以同时推进，以便互不相关的工作不互相阻塞。

### 回执、完成与验收

48. 作为用户，我希望执行者每轮提交结构化回执（结论、证据、继续或交接、提问、预约复查、申请完成），以便运行时根据事实而不是猜测推进。
49. 作为用户，我希望重复或过期的回执只生效一次、不覆盖新状态，以便崩溃重试不制造混乱。
50. 作为用户，我希望回执缺失或格式错误时保留已完成的产物，显示协议异常等待处理，而不是重做业务，以便不重复副作用。
51. 作为用户，我希望执行者申请完成时逐项核对完成条件并附证据，可确定检查的条件必须通过检查，以便 Done 有据可查。
52. 作为用户，我希望可以选择人工验收，验收通过才进 Done，退回时记录原因并继续推进，以便重要任务由我把关。
53. 作为用户，我希望模型生成的完成条件不能缩小我的目标，我也能查看和修订，以便不会被“降低标准”的完成蒙混。
54. 作为用户，我希望失败、超限或取消的任务也保留阶段成果、未完成项和原因，以便不因失败丢失已做的工作。
55. 作为用户，我希望定时复查能把任务按时唤醒回原任务，且不写系统调度器，以便需要等待外部结果的任务能自动接着做。

### 预算、交接与失败

56. 作为用户，我希望任务累计预算覆盖所有模型调用（负责人协调、成员、辅助、压缩、重试），换成员、暂停恢复或回答问题都不清零，以便总花费可控。
57. 作为用户，我希望用量统计缺失时显示缺口并阻止无界自动推进，而不是当作零，以便预算不被漏算。
58. 作为用户，我希望启动前看到具体的累计 token 上限和单轮限制，以便知道最多花多少。
59. 作为用户，我希望成员交接默认最多 8 次，首次分配和负责人纯调度不计，以便防止团队来回踢皮球。
60. 作为用户，我希望预算耗尽或交接即将超限时停止派发并显示原因、计数和阶段成果，我追加额度后才继续且不清零原账本，以便超限不会悄悄继续花钱。
61. 作为用户，我希望只有确认安全的临时故障才自动退避重试，最多 3 次并显示下次重试时间，重启不重置次数，以便故障处理既自动又有边界。
62. 作为用户，我希望审批拒绝、成员不可用、超限、配置错误和结果不确定的副作用不被盲目重试，以便不放大问题。

### 审批、暂停与修订

63. 作为用户，我希望新任务的审批策略可选“拒绝”或“挂起等待”，默认挂起，以便无人值守时既安全又不轻易中断。
64. 作为用户，我希望业务拍板和工具权限审批分开，审批内容说明问题、影响和可选操作，以便我清楚在批准什么。
65. 作为用户，我希望拒绝只禁止该操作，执行者可以找已授权的替代方案，没有时保持阻塞，不反复申请同一被拒操作，以便拒绝有效且不被骚扰。
66. 作为用户，我希望等待审批或等我回答时释放执行资源、不调用模型，以便长时间等待不浪费。
67. 作为用户，我希望批准、拒绝、过期、取消、重启和重复点击都有明确结果，过期不等于批准，以便审批状态可信。
68. 作为用户，我希望任务关闭或权限撤销后，迟到的批准不能再启动执行，以便收回的授权真正生效。
69. 作为用户，我希望暂停时先停止派活，再让当前 Agent 在安全边界停下，期间显示“正在暂停”，真正停下才显示“已暂停”，以便状态不撒谎。
70. 作为用户，我希望恢复从已确认成果继续，不重跑整个任务，结果不确定的副作用进入恢复审核而不自动重放，以便恢复安全。
71. 作为用户，我希望取消同样区分请求中与已停止，迟到的回执或唤醒不能复活已取消任务，以便取消可靠。
72. 作为用户，我希望修改目标、完成条件、执行者、分工、目录或预算前必须先暂停，保存版本和修订记录，恢复时由执行者核对旧成果，以便修订可追溯且不打乱进行中的工作。
73. 作为用户，我希望更换执行者不会自动继承原执行者的权限，以便换人不扩大授权。

### 重启与旧计划

74. 作为用户，我希望服务崩溃或重启后，可确认安全的等待和排队工作自动恢复，结果未知的写操作进入恢复审核，以便重启既不丢工作也不重复写。
75. 作为用户，我希望审批、计数、成果和详情都能从持久化状态重建，以便重启后一切照旧。
76. 作为用户，我希望旧计划按状态出现在对应列，ID、原 Agent 绑定、输入与证据、修订历史、首次批准与权限选择、人工验收和删除限制都保留，以便升级不丢东西。
77. 作为用户，我希望已完成的旧计划出现在 Done 而不是因旧的“归档”投影消失，以便历史成果可查。
78. 作为用户，我希望旧计划继续按原路径和原有修订、执行者绑定限制执行，不被改成 Team 或新默认验收方式，以便旧任务行为不变。

### 后续来源（第二阶段起）

79. 作为用户，我希望后续通过 GitHub 插件把 Issue 自动转成 Todo 并指定 Agent／Team，以便记录问题就等于交出任务。
80. 作为用户，我希望飞书或 Google 表格里填一行就通过插件生成 Todo，并由插件把任务状态回写到表格，以便在熟悉的工具里管理来源。
81. 作为用户，我希望插件来源的 Todo 带来源、外部 ID 和来源链接，用于去重和追溯，以便同一个 Issue 不会生成两张卡片。
82. 作为用户，我希望周期性工作（如每日 SEO 复盘、每日内容调研）按时生成新的 Todo 再走同一个执行器，以便定时任务也有完整的执行记录和成果。

## Implementation Decisions

### 领域与总体架构

- 看板任务（Kanban Task）是 Durable Execution 的一种任务形态，复用并扩展其目标身份、版本、租约、预算、审批、证据和恢复基础；单 Agent 与 Team 是执行方式。不为 Team 建立第二套目标状态、预算或审批真相来源，不新建进程外编排器。
- Runtime Task（定时／提醒）与 Mini App Todo 的含义不变（ADR 0003）；Runtime Task 的 `todo` 类型不是看板 Todo。存储遵循按域数据库（ADR 0004）与 Pi 私有执行存储（ADR 0005）。
- 看板阶段是投影：任务状态由共享执行聚合持有，看板列、协作记录、对话视图和进度面板都从持久化状态派生。资源占用、运行数和自动恢复读取真实运行状态，不依据看板列判断。
- 渠道层不参与；任务入口是 Desktop 与共享服务层。临时运行控制不写入普通会话消息；结构化排障事件不回灌模型。

### 模块划分

- **看板任务服务**：在现有计划共享服务之上扩展（UI 与模型工具都经此层），新增：创建看板任务（单 Agent／Team、负责人、Project 或工作目录、完成条件、预算、交接上限、审批策略、人工验收、自动开始）、启动、看板列表（三列与已取消投影、全集筛选与计数）、回答／补充资料、追加额度、人工验收与退回。暂停、恢复、取消、删除、修订沿用现有协调器语义。
- **执行运行时**：沿用 Durable 运行时与持久化唤醒队列／worker。新增看板任务的推进循环：根据最新回执决定续轮、交接、等待、复查或结案；每次派发前做权限、状态、预算、交接上限与 Project 推进位检查。
- **成员执行适配**：Team 成员的一次工作复用 Room 的 Agent 运行构造（成员 Agent 配置、模型、身份、Project 与权限收敛规则），但使用任务专属的成员上下文，不写入 Room 会话记录，不依赖 Room 当前打开状态。
- **提示词合成**：沿用现有合成链路，不新增流程字段。负责人轮次使用负责人的合成规则；成员轮次使用成员自己的合成规则；任务简报（目标、完成条件、分配内容、已有成果、清单）作为本轮输入，不进入需要缓存稳定的前缀。
- **Desktop 看板**：现有计划工作区升级为看板与详情；详情主区复用现有对话消息流组件渲染任务对话投影，右侧为进度面板；API 统一经 Desktop API 客户端。

### 创建与启动

- 启动时在一个事务内保存配置快照（目标版本、执行者、成员、负责人、工作目录、预算与交接上限、审批策略），并写入持久化唤醒；提交后才派发。启动按操作 ID 幂等。
- “自动开始”开启时创建与启动在同一操作完成；关闭时只创建，状态为 planned（Todo）。配置不完整或被拒时保留在 Todo 并返回原因。
- 负责人默认取 Team 的 Primary Agent，可在创建时改为其他成员；负责人必须是成员。Primary Agent 本身仍只代表 Room 默认接收者，负责人是任务配置里的独立角色。
- 配置快照不冻结安全授权：Agent 禁用、删除或权限撤销在每次派发前重新校验并立即生效。

### Project 推进位

- 同一 Project（无 Project 时按规范化后的工作目录）同一时刻只有一个看板任务持有推进位。推进位作为持久化状态与任务状态在同一事务内获取和释放。
- 持有期间包括执行、等待审批、等待用户、等待复查、暂停与已停止（失败、部分完成、超限、恢复审核）；进入 Done 或已取消才释放，随即按创建顺序唤醒下一个排队任务。
- 排队任务处于 Doing／排队子状态，详情显示被哪个任务占用。旧计划沿原路径执行，不参与推进位。
- 推进位是看板任务之间的约束，不替代既有工作目录权限与冲突保护，也不约束普通对话或 Room 的写入。

### 执行循环与回执

- 单 Agent：在任务专属上下文中按回执续轮、等待或复查；缺少有效后续意图或完成证据时进入等待用户确认，不隐式续跑。
- Team：负责人轮次产出“交给某成员 + 本次简报”或“退回／复查／提问／申请结案”；运行时派发成员轮次；成员回执交回负责人。任务内任何时刻只有一个有效推进者和一个有效配置版本。负责人亲自做业务工作时按成员规则计数，协调与业务分开计数。
- 回执通过任务作用域的结构化工具提交，绑定任务、执行轮次与配置版本。动作可组合：结论、证据、继续／交接、提问、通知、关闭已解决问题、预约或取消复查、申请完成、维护进度清单。同一阻塞的未关闭问题不重复创建。
- 运行时确定性校验后，在现有聚合事务内一并提交执行结算、已消费输入、预算、状态、推进位与下一次唤醒，提交后才派发。重复提交只生效一次；同一回执身份内容冲突时拒绝；旧版本结果不覆盖新状态。
- 回执缺失或格式错误：保留产物与执行结果，标记协议异常，等待安全修正或用户处理；成员完成不自动把主任务置为 Done。
- 定时复查复用持久化唤醒（`verify`／`resume` 等原因），补跑与超窗遵循既有恢复约束；回答、审批决定与到期复查都回到原任务，不重置预算或交接计数。

### 进度清单

- 清单是任务的一项持久化状态，由单 Agent 或负责人通过回执增删改与勾选，带版本，重启可重建。
- 清单独立于计划步骤（ExecutionStep）：不带步骤验证规则，不驱动调度，不是 DAG；全部勾选不等于满足完成条件。旧计划继续展示其原有步骤。
- 简单任务允许没有清单；卡片只在有清单时显示勾选数／总数。

### 对话视图

- 任务对话是只读投影：按时间合并该任务所有成员上下文中的消息、工具活动、审批与交接事件，每段标注成员；完整内容可展开，复用现有对话消息流组件与文件预览。
- 用户在详情中的输入作为任务的待消费输入持久化，由下一次执行消费；第一版不实时 steer 正在运行的轮次，不改目标。
- 任务执行上下文不进入普通会话列表。

### 看板投影

| 列／范围 | 进入条件 | 子状态示例 |
| --- | --- | --- |
| Todo | 已创建未启动（自动开始关闭或启动被拒） | 待启动、配置待补齐 |
| Doing | 已启动但未满足完成条件 | 排队（含等待同 Project 前序任务）、执行、验证、等待审批、等待用户、等待复查、等待重试、暂停、异常、预算／交接超限、恢复审核、待验收 |
| Done | 完成条件全部通过，且要求的人工验收已通过 | 已完成 |
| 已取消（默认收起） | 已取消 | 已取消 |

旧计划投影（原始状态与看板阶段分开保存，现有 planStatus 中 completed → archived 的标志不得作为看板过滤条件）：

| 原始 execution.status | 看板 |
| --- | --- |
| planned | Todo |
| queued、running、verifying | Doing，保留排队／执行／验证子状态 |
| waiting_for_user、waiting_for_approval | Doing，保留决策／验收／审批类型 |
| paused、recovery_required | Doing，保留暂停／恢复审核 |
| partial、failed | Doing，明确已停止且不会自动运行 |
| completed | Done |
| cancelled | 已取消 |

- 拖入 Doing 等同启动；拖入 Done 被拒绝，只能经完成检查进入。
- 删除沿用旧计划的删除限制与墓碑语义。

### 完成与验收

- 默认自动验收：单 Agent 或负责人申请完成时附完成条件逐项核对与证据；确定性条件必须通过检查器；证据缺失、仍有必需工作或运行状态不确定时拒绝进入 Done。
- 未填完成条件时，启动阶段先由执行者生成可见条件；无有效条件时等待用户补充，不开展实质工作。生成的条件不得缩小用户目标，用户可按修订规则调整。
- 人工验收任务停在 Doing／待验收，用户确认后进入 Done；退回记录原因并继续推进，不覆盖旧成果。
- 最终交付至少包括结论、完成条件核对、产物或证据引用、未验证项；失败、超限、取消同样保留阶段成果。

### 预算、交接与失败

- 三类计数分开持久化：执行轮次（同一成员内部续轮、等待恢复、模型执行）；成员交接（默认上限 8，首次分配与负责人纯调度不计，A→B、B→A 各加一，续轮、重试、回答、复查不计）；事件因果深度（为后续跨任务派生预留，本版不开放派生）。
- 累计预算与每轮运行预算同时生效，所有模型调用计入；用量缺失记为统计缺口并阻止自动推进。每次模型调用前检查额度，结算后再检查；无法严格限制单次请求超额时在 UI 说明边界。具体默认值（累计 token 上限、单轮限制）取现有预算配置的有界默认值，在技术设计中定下并写入验收，缺省不解释为无限。
- 下一次交接将超上限或预算耗尽时停止派发，Doing 显示原因、计数与阶段成果；用户追加额度后继续，追加单独记账，不清零。
- 临时故障仅在确认未执行或幂等／可查询确认安全时退避重试，初次失败后最多自动重试 3 次，计入预算，下次时间可见，次数持久化。审批拒绝、成员不可用、超限、不可恢复配置错误、结果不确定的副作用不重试；CR 返工不计入故障重试。

### 审批、暂停与修订

- 新手动任务审批策略可选 deny／suspend，默认 suspend；旧无人值守任务保持原有拒绝策略。
- 业务拍板与工具权限审批分开保存；工具审批绑定请求、执行身份、范围与参数。拒绝结果交回执行者，可寻找已授权替代方案；不得循环申请同一被拒操作。
- 等待审批或等待用户时释放 runner、执行租约与连接，不产生模型调用；通知与界面轮询不调模型。不能沿用 Room 当前的无限 inline 等待，必须验证真实释放资源。批准、拒绝、过期、取消、重启与重复点击有唯一消费方；过期不视为批准；任务关闭或权限撤销后迟到批准不能启动执行。普通审批与 Durable attempt 的不同恢复方式由共享层适配，不要求所有路径保留原 runId。
- 暂停：先停止派活，再请求当前 Agent 在安全边界停止；当前工具结束或其不确定结果已记录、写入者已停止后才为“已暂停”。不确定副作用进入恢复审核。取消同样区分请求中与已停止，停止后进入已取消并保留成果。
- 关键修订（目标、完成条件、执行者、分工、目录、预算）须先暂停，保存版本与修订记录；恢复前由负责人或新单 Agent 核对旧成果；新配置不应用于旧的已认领执行；更换执行者不继承原权限。旧计划沿用原有修订与执行者绑定限制。

### 持久化与升级

- 全部为加法 schema 升级与兼容读取，保持旧记录原语义；新增内容包括看板任务配置快照、Team 成员与负责人、成员任务上下文引用、回执与去重键、交接与预算账本、进度清单、待消费用户输入、Project 推进位、自动开始标记，以及为后续来源预留的来源类型、外部 ID、来源链接。
- 实施前为实际存储变更明确备份、升级与失败恢复方案。不自动重写旧目标、迁移旧 Agent 绑定或将旧计划改为 Team。源 Room 不是任务成果与运行状态的真相来源。
- 租约、状态版本、回执去重、预算与下一次唤醒覆盖进程崩溃窗口；执行结果未知时进入恢复审核，不默认重新执行写操作。
- 若新增或修改 settings 字段，遵循整对象持久化 round-trip 守卫。

### API 契约（方向）

- Desktop 计划 API 扩展为看板任务 API：创建（含自动开始）、列表（列投影、全集筛选与计数）、详情（配置、状态、清单、成果、计数）、对话投影（分页、按成员标注）、启动、回答／补充输入、审批决定、暂停／恢复／取消、修订、追加额度、人工验收／退回、删除。所有写操作带期望版本与操作 ID；实时更新沿用现有 SSE 推送与重连快照对齐。

## Testing Decisions

### 好测试的标准

- 只测外部行为：通过服务公开入口和 HTTP/UI 观察状态、看板投影、对话投影、计数与持久化结果，不断言内部函数调用顺序或私有表结构。
- 全部使用临时数据库、隔离数据目录与本地模拟模型；不调用真实 Provider 或第三方账号，不修改用户服务。
- 崩溃与重启通过重新构造 store／runtime 模拟，不依赖时间巧合。

### 测试接缝（Seams）

1. **主接缝：看板任务服务 + 真实 Durable 运行时 + 本地模拟模型**。在这一层驱动创建、启动、回执、交接、等待、审批、暂停、重启与结案，覆盖绝大多数行为。先例：计划服务测试、Durable 运行时／协调器／唤醒 worker 测试、Pi 执行测试、Room runtime 集成测试的 fixture 与模拟模型。
2. **界面接缝：Desktop HTTP API + Playwright UI**。只覆盖看板交互、拖动语义、详情对话与进度面板渲染、冷启动与断连恢复。先例：现有 plans／workspaces 系列 UI 用例。

不为成员执行适配、推进位、清单等内部模块单独开接缝，除非主接缝无法稳定构造对应场景。

### 覆盖范围

1. **创建与启动**：自动开始开启时创建即进入 Doing 且只派发一次，重启后不丢、不重复；关闭时留 Todo、不调模型；重复启动只产生一个执行；单 Agent 与 Team 都能真实进入 Doing。
2. **同 Project 串行**：两个任务按创建顺序串行；前者等待、暂停或停止时后者保持排队并显示占用者；前者 Done／取消后后者开始；不同 Project 并行；旧计划不受推进位影响。
3. **流程来源**：渲染后的提示词包含项目 AGENTS.md（无项目级文件时为全局与 Agent 规则），负责人与成员各用自己的合成规则，无重复章节，任务简报不进入缓存前缀。
4. **团队闭环**：模拟方案 → 编码 → CR 退回 → 编码修改 → CR 通过；负责人默认取 Primary Agent；只有一个主任务，成员串行，完成后 Done 且可读成果；Room 会话记录不被写入。
5. **护栏**：首次派活不计交接；第 8 次允许、第 9 次被阻止；负责人调度、重试与压缩计预算；换成员与回答不清零；用量缺失阻止推进；超限只在显式追加后继续。
6. **回执与崩溃**：重复提交、版本冲突、状态提交与派发之间重启、重复唤醒；不丢后续工作、不重复确认成果、不重放未知副作用；格式错误回执保留产物并显示协议异常。
7. **等待与审批**：业务问题、Broker、Host Bash、批准／拒绝／过期／迟到决定、重启后回答；等待期间无模型调用且释放实际 runner 资源；拒绝不升级权限，不重复申请同一被拒操作。
8. **暂停、取消与修订**：暂停请求中不伪报已暂停；恢复不重做成果；取消后迟到回执不复活；关键修订须先暂停并产生版本；修改源 Team 不影响已启动任务；权限撤销立即生效。
9. **失败**：仅安全故障最多自动重试 3 次，退避与计数持久化；CR 返工不是故障重试；未知效果转恢复审核。
10. **完成与验收**：补齐条件后才开展工作；检查失败或证据不足不进 Done；清单全勾不等于完成；人工验收与退回；失败／取消仍可查阶段成果。
11. **进度清单与对话投影**：清单增删改与勾选持久化并在重启后重建；简单任务无清单；对话投影按时间合并各成员内容并正确标注；用户补充输入被下一轮消费且只消费一次。
12. **旧计划**：临时库升级／重新打开后 ID、绑定、验收、证据与修订保持；所有状态映射正确；旧 completed 出现在 Done。
13. **桌面**：创建（含自动开始开关）、筛选与全集计数、已取消区域、拖动语义、详情对话与进度面板、成果预览；改动包 svelte-check 无新增问题；隔离实例冷启动后首次打开／点击、页面切换、断连恢复状态与可操作性正确。

涉及 settings 时加 save → 新建 store → load 整对象回归；涉及 Tauri capability、CSP、HTTP scope 或原生命令时运行相关原生用例并做 Rust 重建。完整 verify:feature、完整 Playwright 与完整原生套件由用户在整体验收／发版前执行。

## Out of Scope

- GitHub、飞书多维表格、Google 表格等 trigger 插件、来源轮询、AI 分流与触发源管理（第二阶段起；本版只预留来源字段）。
- 定时自动生成 Todo、从聊天自动声明任务、新增聊天声明工具；现有定时任务保持原执行方式。
- 运行时内置的结果回写与对外发布步骤：关闭 Issue、提 PR、发布网站或草稿由用户在流程中声明，执行者用已授权工具完成；表格类来源的回写由对应插件负责。
- 多成员并行、工作项 DAG、固定流程编辑器、独立 Team 模板管理器。
- 同一 Project 多任务并行（如独立 git worktree）。
- 运行中实时 steer 改目标、跨任务自动派生与复杂依赖调度。
- 强制工作项分解、规模化批量验收。
- 渠道（Telegram／飞书／QQ／微信）入口与通知。

### 分期

- **第一阶段（本 Spec）**：看板与已取消区域、自动开始、对话式详情与进度清单、流程沿用 AGENTS.md、单 Agent 与串行 Team、同 Project 串行、全部护栏、旧计划纳入。
- **第二阶段**：插件创建协议与 GitHub Issue 插件（去重、来源链接）；周期模板按时生成 Todo，复用现有运行时事件调度，不另造调度器。
- **第三阶段**：飞书、Google 表格插件及其状态回写。

后续插件通过共享创建入口提交任务，选择获授权的 Agent／Team，可订阅任务状态变化完成回写，但不另建执行循环、不控制执行过程。
