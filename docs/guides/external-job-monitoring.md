# 外部任务监控与超时反馈

提交内容、触发 CI 或创建生成任务后，先向用户报告已经确认的成果和结果地址／任务 ID，再说明当前等待什么。提交成功、推送成功和发布成功是不同状态；只有外部系统确认成功，才报告对应任务完成。

## 查询既有任务

优先做有时限的状态查询，避免用一条长时间阻塞的命令覆盖整个等待过程。例如查询 GitHub Actions：

```bash
gh run view <run-id> --repo <owner>/<repo> --json status,conclusion,url
```

外部任务仍在运行时，说明“内容已提交；CI 正在运行，发布尚未确认”，附任务链接。查询超时说明最后确认的状态和待确认事项；下一次查询同一任务，不重新提交内容或创建任务。

需要稍后跟进时，通过 `runtimeTask` 创建已获授权的运行时任务。创建成功后才报告后台监控已启用，保留任务标识；不能用聊天里的承诺、memory 或 OS scheduler 代替。未实际安排跟进时，不能说“仍在后台监控”。

## 执行异常后的报告

共享 Runner 在异常结束时输出并保存最近的进度说明、最近五个成功工具结果摘要、未返回结果的步骤和停止原因。曾失败的步骤单独列出，不视为一定尚未完成；它们可能已被后续步骤恢复。报告进入会话和运行摘要，重新打开会话仍可查看。

工具返回成功只确认该步骤。运行时不从命令标签或退出码推断整个任务已经完成，也不因本地查询超时断言远端任务失败。未知写操作仍保留恢复保护；本次输出改进不改变 Bash 的副作用分类，不自动重试未确认的写操作。

验证覆盖原生 Runner／Pi 的成功回执、进度消息、准备阶段结果未知、异常报告持久化和不重放操作。进入监控前的自然语言说明及短查询方式由系统提示词指导；模型是否遵循不能仅靠提示词保证。

## 历史会话显示

只有工具过程、没有最终正文的回合仍保留在历史中。回答与用户输入按同一轮次关联；即使旧记录已保存错误的来源 ID，也不能把下一次输入或回答挪到上一轮。错误关联会在重新加载会话时按原始记录校正。

最近运行摘要中的终态用于校正显示状态，并补齐已保存的最终结果。监控超时的执行显示异常，不从成功工具数量推断整个执行成功。不同用户轮次各保留自己的过程与答复，不为消除视觉上的两条记录而合并。
