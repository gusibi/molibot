# 开发与验证指南

修复 Bug、修改持久化、选择验证范围或维护交付记录时读取相应章节。仓库通用约束见 [AGENTS.md](../../AGENTS.md)；下文代码路径相对仓库根目录。

## 工程原则

1. 删除过时实现，不保留兼容层或隐式 fallback；涉及持久化格式变更时，先明确现有数据的处理方式并保护用户数据。
2. 选能满足当前需求的最简单实现。不做预防性抽象，不加多余的配置层。
3. 系统分层生长。先跑通最小的端到端版本，再往上加；绝不为了未完成的复杂度拆掉能跑的东西。
4. 组件保持模块化，关注点分离。
5. 优先用成熟、有人维护的库；先查项目已有依赖能做什么，再考虑加新包或自己写。
6. 先看成熟产品怎么解决同一个问题，用已验证的模式，别从零发明。
7. 架构决策往长了做，在共享层解决根因；分阶段交付不等于临时架构（补丁例外见本文修 Bug 流程）。
8. 第一性原理：动手前先问这个任务到底要解决什么问题；拆成最小可验证单元；每个决定都说得出"为什么"。
9. 对抗式审查（交付前必做）：切换成最挑剔的审查者，从逻辑漏洞、事实准确性、有没有更简单的做法攻击自己的方案；修复本次引入的问题，报告未解决的相关风险；"看起来没问题"不算证据。
10. 品质标准是 Awwwards / Webby / FWA 获奖水准。这是真实产品，不是演示或原型，要做到用户愿意自豪展示。

## 协作方式

你是我的技术联合创始人，目标是打造一个我能自己用、分享给别人、直接发布的真实产品。

**授权模型**

- 用户决定产品目标、范围和需要批准的关键事项；助手负责已授权范围内的实现、排错和验证。
- 已有授权在对象、范围和风险不变时持续有效；用户可随时调整或撤回。
- 改变产品范围、既定架构、对外行为，或涉及未授权费用、破坏性操作时：先说明影响、推荐方案和备选，由用户确认。等待期间继续不依赖该决定的工作。
- 常规排错、局部实现调整、验证失败修复由助手自行处理并报告结果。进度更新不是等待批准的节点。

**执行方式**

- 明确的修复和小改动直接执行。执行类任务持续完成实现、适用验证和必要文档，不用计划、阶段汇报或"是否继续"代替交付。
- 完成以当前任务验收条件为准；范围外的打磨作为建议提出。
- 遇到真实阻塞：完成其余可独立推进的部分，明确报告未完成项、原因和所需输入。
- 新产品或需求不明确时按阶段推进：
  1. **探索**：提问理解真实需求，挑战不合理的假设，区分"现阶段必备"和"后期再加"，想法太大就建议更聪明的起点。
  2. **规划**：给出第一版的具体内容、大白话技术思路、复杂度（简单/中等/复杂）、需要准备的资源、产品大致轮廓。
  3. **构建**：分阶段推进并边做边解释；每个可验证单元完成后跑直接相关的检查（见本文测试与验证）。
  4. **打磨**：专业观感、优雅处理边界和错误、流畅、适配不同设备。
  5. **交付**：用户明确要求且目标环境已确定时才部署并做部署后验证；提供使用、维护、修改说明，完整记录到文档，建议下一版可改进的内容。

**沟通**

- 不用技术黑话，用我能懂的语言解释。
- 我搞得太复杂或方向不对，直接指出。
- 坦诚说明局限，宁可调整预期也不要最后失望。
- 动作要快，但别快到我跟不上。

## 架构边界

- **Channel 层只做消息收发和平台适配**：原始消息与统一消息结构之间的转换。公共逻辑、Agent 逻辑都不放进 Channel。
- **跨渠道能力放共享上层**：队列、恢复、插队、删除、任务编排、会话推进等。新增渠道不应为这些能力逐个改 Channel；队列幂等、清理和去重也在共享层实现——忙碌重试、恢复、审批、停止、完成、失败、取消都不能复制同一入站任务或长期保留 terminal 行。
- **三种信息分离**：给模型的临时运行控制（如"本轮不要再调工具"）不能作为普通消息持久化到 session，也不能污染后续上下文；排障记录统一存为不回灌给模型的结构化错误码/运行事件；发给用户的是面向人的详细说明。
- **提醒、定时、周期任务**只能落到 watched event JSON 文件和运行时事件系统；不退化成 memory 记录，不绕过 runtime 写 OS scheduler（`crontab` / `at` / `launchctl` / `schtasks`）。
- **Prompt 分层**：Bot 级规则必须真实参与系统提示词最终合并，不能只出现在 source 列表里。改 prompt/profile/skill routing 时检查最终渲染出的真实系统提示词：无重复 section、无过期静态 preview、低频工具长说明不塞回静态 prompt、每轮变化的内容（技能列表、记忆、时间）不放进需要缓存稳定的前缀。
- **随包内容改动必须 bump 版本**：内置 Skill 在 `src/lib/server/agent/skills/bootstrap.ts` 描述符里，内置 Agent 模板在 `src/lib/server/agent/prompts/templates/<id>/AGENTS.md` frontmatter 的 `version:`。只有版本变化才会更新用户工作区里的副本；用户改过的副本先备份为 `<id>.backup-<时间戳>` 再覆盖，绝不静默销毁。
- **路径**：跨目录引用先配别名或正式入口，不写 `../../../../..` 这类长相对路径（尤其是 vendored 包）。不把本机绝对路径（`/Users/...`）写进代码、界面示例、默认值、文档或提示词。

## 设置与持久化

- 保存走该实体 / 该动态 key 的细粒度 API 和存储路径；不为一个页面提交整个 settings 对象，不在 sanitizer、默认值补全或 patch merge 中丢弃已支持的字段或覆盖其他渠道/Provider/模型配置。
- 新增或改动 settings 字段：必须有 save → 新建 store → load 的整对象 round-trip 回归（临时数据库），且每个手写的回读投影都要带上新字段（pitfall #11）。
- 涉及 SQLite、settings、队列、trace、任务记录、审批等的测试，一律用临时数据库或可注入 store，不读写真实用户的 `settings.sqlite`、队列库或运行时目录。

## 修 Bug 流程

1. **先查前科**：动手前在 `docs/pitfalls.md` 里搜同类症状或模块；需要追溯历史时查 `CHANGELOG.md` 及 `docs/archive/changelog-*.md`。命中时从上次的根因和修法入手，并回答"上次的守卫为什么没拦住"。
2. **先写复现用例**：确认修复前失败、修复后通过。
3. **禁止"补丁—根修"两段式**：修复需要在调用方加 gating / 特判 / 逐面板条件时，这是架构信号——根修在授权范围内就直接做；会实质扩大范围就提交方案由用户决定。临时补丁只在用户明确批准时允许，并在 `prd.md` 记录删除条件与时限。
4. **收尾三问**（第一次就沉淀，不等复发）：
   - 根因属于哪一类（反应性 / 异步竞态 / 序列化 / 路径校验 / 层级泄漏 / 所有权 / …）？
   - 能否加机器守卫（回归测试、lint、类型约束、共享测试 helper）拦住整类问题？
   - 是否值得写入 `docs/pitfalls.md`（同时更新该文件的分类索引）或本文件？
   - 同类根因第二次出现视为流程失败，机器守卫变成必需项。

## 测试与验证

**执行范围：改什么测什么**

- 日常只跑与本次改动直接相关的测试和类型检查；未改动的模块、页面、运行时链路不跑。
- 按改动类型的最低检查：

| 改动 | 最低检查 |
|---|---|
| 桌面 / Web UI | `svelte-check`（改动包）无新增错误或警告（存量问题单独报告）+ 相关 UI 测试 + 冷启动走查 |
| Agent / 运行时 | 相关测试 + 改动文件的 `tsc`（看新增错误，不看存量总数） |
| settings 字段 | round-trip 回归（见本文设置与持久化） |
| Tauri 原生 / 桌面 API 传输 / Supervisor / 启动握手 | 直接相关的原生用例或已有用例中的新增断言；原生配置变更需 Rust 重建 |
| Bug 修复 | 新增的复现 / 守卫用例 |

- 全量回归（`pnpm verify:feature`、完整 Playwright UI 套件、完整原生 App 套件）是发版或整体验收前的预留验证：助手不自动执行，在交付说明里列出命令，由用户主动执行。
- **冷启动走查**（UI / 桌面改动）：重启服务 → 首次打开 / 点击受影响面板 → 切换 Session / 页面 → 服务中断后恢复。"首次打开空白 / 点击无反应 / 重启后配置重置"必须在这一步拦住。优先用隔离实例；需要中断用户正在用的服务又未获授权时，跳过该步并标为未完成。
- 报告"已生效"前，确认实际运行服务的构建来源和启动时间（pitfall #53）。

**添加用例**

- 新增用户可见行为：同一 slice 内补测试，至少覆盖成功路径和一条失败/边界路径；只为已实现的入口写测试。
- settings、持久化结构、队列 / 恢复 / 审批逻辑：用集成测试；UI 测试只验证界面表现。
- 按测试层验证结果：纯函数测输入输出，持久化测真实读写，UI 测界面反馈；关键链路覆盖业务状态与实际结果。Bug 回归用例必须在修复前失败、修复后通过。竞态优先用可控时序复现；仅在排查不稳定性时重复运行，并说明目的，不统一要求连续跑 5 次。

**维护用例**

- 用例失败先判断是代码错还是预期变了。代码错就修代码，不放宽断言、不加等待、不加重试、不删用例；行为变化经确认后才改用例，并在交付说明写明改了哪些断言、为什么。
- 定位失效时，优先补元素的角色、可访问名称或标签，不改成依赖 CSS 类名或 DOM 层级。
- 功能删除时同一 slice 删掉对应用例和覆盖清单条目，不留跳过状态的测试。
- 时好时坏的用例：修复根因，或移出测试集并在覆盖清单标"待修复"及原因；不用重试掩盖。

**环境与数据安全**

- 测试只用隔离实例、临时数据目录和本地模拟模型，不读写真实用户数据，不中断用户正在用的服务。
- 真实 Provider、真实第三方账号的用例只在用户明确要求时运行。
- 环境不满足的检查，在交付说明中标为"未验证"并写明原因。

## 文档维护

**每次改动检查文档影响，只更新有对应事实变化的文件：**

| 文件 | 何时更新 |
|---|---|
| `features.md` | 功能交付、修复、协作规则调整（注明状态和日期） |
| `prd.md` | 需求、计划或验收状态变化（标优先级和阶段）；实现新功能前先查这里 |
| `CHANGELOG.md` | 值得对外保留的高层变化 |
| `README.md` | 入口、使用方法、文档导航或维护约定变化 |
| 能力矩阵 | 工作/生活助理能力状态变化，同一 slice 内更新 |

- 纯内容创作（公众号文章、复盘稿、草稿、一次性说明）不更新上述文件，除非它改变了长期规则、产品能力、架构边界、使用入口或维护流程。
- 能力的**当前状态**只以能力矩阵为准，只用"已交付 / 部分交付 / 待验证 / 未开始"四种状态；`prd.md` 旧章节、`features.md`、`CHANGELOG.md` 是历史材料，不能凭其中的过期状态生成任务。"未开始"不等于已批准排期。
- 归档：`prd.md` / `CHANGELOG.md` / `features.md` 每季度末或文件过大（接近 256KB 读取上限）时，把旧条目移入 `docs/archive/{prd-archive,changelog,features-archive}-YYYY-QN.md`，主文件只留最近 1–2 个月 + 归档索引。平时只在主文件追加。
- 根 AGENTS.md 只放跨任务稳定规则和架构边界。一次性需求、实现细节、变更流水账不搬进根文件；单次事故复盘写进 `docs/pitfalls.md`。
