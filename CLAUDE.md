## Quick Rules

- Layer separation: Channel layer is **messaging only**; shared upper logic (queues, recovery, task orchestration) must not leak into channels.
- Frontend: use Shadcn components from `src/lib/components/ui`. Custom app-level styles must use semantic class names (see DESIGN.md).
- **All toggle/switch controls must use `IosSwitch`** (from `$lib/components/ui/ios-switch`). Do NOT use the generic `Switch` component — its styling does not clearly convey an on/off state. `IosSwitch` provides the expected iOS-style toggle appearance.
- Never hard-code absolute paths (`/Users/...`) into code, docs, or prompts.
- After any feature change, update `features.md` and `CHANGELOG.md`. (Old entries in `prd.md` / `CHANGELOG.md` / `features.md` are archived quarterly in `docs/archive/`).
- Bug fixes: BEFORE debugging, search `CHANGELOG.md` (+ archives) and the pitfalls below for prior occurrences of the same symptom/surface. BEFORE merging, answer the "Fix 收尾三问" in AGENTS.md §开发流程沉淀规则 (root-cause class → machine guard → pitfall entry). A second occurrence of the same root-cause class makes a machine guard mandatory.
- No band-aid-then-root-fix: if a fix needs caller-side gating/special-casing instead of a shared-layer solution, either do the root fix now or file it in `prd.md` with the band-aid's removal condition.

## Recurring Pitfalls (distilled from CHANGELOG.md / prd.md — read BEFORE touching these areas)

Each item below caused **multiple** shipped bugs. Check the relevant one before writing code.

1. **Session-list leakage** (fixed 4+ times): any surface that lists conversations (sidebar, browser dialog, external `contexts/` projection, more-conversations dialog) MUST filter out automation sessions — `origin: "automation"`, current `t-*` or legacy `task-*` session keys, legacy `[EVENT:...]` first-message sessions — and keep only `purpose === "conversation"`. Do the filtering in the shared query layer (`src/lib/server/app/desktopConversations.ts` / `externalSessionsFromContexts.ts`), never per-channel or in UI.
2. **Svelte 5 reactivity** (fixed 3+ times): a legacy `$:` derivation does NOT subscribe to runes `$state` from another module — it runs once and goes stale (symptom: blank on first open, works after a round-trip). New components use runes (`$props`/`$state`/`$derived`); legacy surfaces read live controller state only through its `view` store (`$conversationView` pattern). Never call a no-arg helper from a template and expect its internal state reads to be tracked — pass deps explicitly. Never trigger the same async load from both `onMount` and a `$:` block (they race on init). Corollary (fixed 2+ times, symptom: the composer advertises the global default model while the runtime uses the session's own): a `$:` reading a `toStore` projection re-runs on EVERY store tick because the projection returns a fresh object — gate such loads on the value actually changing (`if (x && x !== lastX)`), and never let a refresh handler reset per-session state (model/thinking selection) to a global default unconditionally. Guarded by `apps/desktop/src/chat-ui.test.mjs`.
3. **Stale async responses** (fixed 2+ times): list/transcript/detail fetches must carry a request generation plus owner IDs (projectId/sessionId) and be validated before mutating visible state; a late response must never replace the currently selected session.
4. **`[data-theme="dark"]` is NOT how you write dark styling** (whole-surface silent failure): `App.svelte` **removes** the `data-theme` attribute when the theme preference is `system` — the default — so a rule written only under `:root[data-theme="dark"] .x` never matches for most users and the surface renders light-on-dark with no error anywhere. There are three theme states, not two: `[data-theme="light"]`, `[data-theme="dark"]`, and *no attribute* (which follows `@media (prefers-color-scheme: dark)`). Style through the semantic tokens (`--card-bg`, `--label-primary/secondary/tertiary`, `--separator`, `--chrome-border`, `--fill`, `--accent`, `--online`, `--danger`, `--warning`) — they are re-declared in all three contexts, so token-based CSS follows every state for free. Reach for a per-theme rule only for a value no token can express (e.g. `--agent-city-sky`, which must match the WebGL clear colour), and then mirror it into **all three** contexts. Status tints use `color: var(--danger); background: color-mix(in srgb, var(--danger) 14%, transparent)`, never a baked light hex. Guarded by the token/`data-theme` assertions in `apps/desktop/src/chat-ui.test.mjs`.
5. **CSS token drift**: referencing an undefined `var(--token)` or keyframe fails silently (no error, just broken styling — e.g. `--shadow-card`, `animation: spin`). Desktop app uses Geist tokens per `DESIGN.vercel.md`; verify a token exists before using it, and snap sizes/spacing to the Geist scale (no 13.5px, no ad-hoc shadows outside the 3 elevation tiers).
6. **Path validation vs. external IDs**: external channel identifiers legitimately contain `@ : + %` (e.g. WeChat `...@im.wechat`). Don't tighten segment/path validation without covering these; conversely, never expose absolute host paths, secrets, or saved API keys to the WebView — return opaque IDs and replace/clear semantics for credentials. Corollary (fixed 2+ times): **one path string must mean one thing in every tool.** `bash` goes through a shell and expands `~`/`$HOME`; `resolveToolPath` used `path.resolve`, so the same `~/x` became `<scratch>/~/x` and failed with a "Path not found" pointing at a path that never existed. Equally, an allowed-roots list is a *product* decision, not a security default: `miniapp-creator` scaffolds into `<dataRoot>/miniapps/apps` and then asks the agent to edit the result, so a guard that omits that root makes the whole workflow read-only through `bash cat`. Whenever a Skill or scaffolder writes outside cwd/Workspace, check the guard in the same change. Guarded by the home-expansion and Mini-App-root assertions in `src/lib/server/agent/tools/path.test.ts`.
7. **Reuse shared modules, no forked copies**: session rows use `ConversationRow`, composers use `ChatInputArea`, completed messages use the shared transcript renderer, turn logic goes through `ConversationController` with a host adapter. Generic shared components must not contain project/channel conditionals — callers inject differences.
8. **CJK handling**: any tokenizer, relevance scorer, or token estimator must handle Chinese explicitly (whitespace splitting collapses CJK to one token; chars/4 under-counts CJK ~3-4x and silently disabled compaction). Use `package/mory/src/moryTokenize.ts` for keyword scoring; weight CJK chars ≈ 1 token when estimating.
9. **Verification convention**: desktop UI changes = `svelte-check` 0 errors/0 warnings + `vite build` + desktop UI tests; agent/runtime changes = agent test suite + `tsc` on touched files. State the results in `CHANGELOG.md` entries.
10. **Cold-start smoke walk** (many shipped bugs were "first open blank / first click dead / reset after restart" — tests and builds passed): after UI/desktop changes, additionally exercise the real cold path — restart the service, first-open/first-click every affected pane, switch sessions, and recover from a service interruption — before claiming done.
11. **Settings round-trip** (fixed 3+ times): every new/changed settings field needs a save → fresh store → load round-trip regression against a temporary database; narrow serialization silently resets fields on restart. The round trip does not end at the database: every hand-written *projection* on the way back — `providerItemToUpdateRequest()` rebuilding the inline editor draft from the saved record, a page's `loadAll()` mapping into its form, that page's own save serializer — must copy the new field too. Any one of them omitting it empties the control the instant the save succeeds, and the next save writes the loss back (issue #28, the model alias). Prefer spreading the source over enumerating fields; where enumeration is required, assert the new field in that projection's unit test.
12. **Out-of-band execution must reuse the in-run context**: an approved Host Bash command can execute from two places — inside the run (`bash.ts`, which holds the agent's real `ctx.cwd`) or from an approval handler after the run ended (`/api/chat` `_handleWebHostToolsCommand`, `baseRuntime`). The out-of-band callers must resolve cwd/project/model through the same helpers the runner uses (`resolveSessionWorkingDir`, `buildRunnerProjectContext`), never re-derive them; picking the chat scratch dir made a project session's `git push` fail with "not a git repository". Guarded by `src/lib/server/agent/hostBashExecContext.test.ts`. Corollary: when the out-of-band path fails, it must still rewrite the suspended toolResult and resume — a failure that only exists in an HTTP response body reaches neither the user nor the agent, and reads as "the button did nothing".
13. **Desktop settings invalidation** (fixed 2+ times): Settings and Chat share one WebView, so a successful Provider/Agent/Profile/model mutation must publish the shared same-document settings event; do not rely on `BroadcastChannel` for local cache freshness. A consumer that is connecting or already refreshing must retain one pending refresh and replay it after settlement instead of dropping the event. Guard the real save → Chat selector seam whenever a settings mutation changes model options.
14. **User cancellation is not an error, and Stop is not a queue reset** (Issue #24): an aborted request's rejection shape is transport-specific — Tauri's HTTP plugin throws a plain `Error("Request cancelled")`, `fetch` throws a `DOMException("AbortError")`, and the server may emit an SSE `error` frame before the client aborts at all. Decide "was this cancelled" from the *intent* flag plus the shared `apps/desktop/src/lib/chat/turnAbort.ts` helper, never from one error class. Equally, Stop ends the current turn only: it must not silently discard queued follow-ups (drain them once the aborted turn has unwound), and a running turn must always offer a way to inject a queued message (`/api/stream/steer` → shared `RunnerPool.steer`) rather than only wait. Guarded by `apps/desktop/src/lib/chat/turnAbort.test.ts`, `src/routes/api/stream/steer/server.test.ts`, and the queue/steer structural guard in `apps/desktop/src/chat-ui.test.mjs`. Second occurrence, same family (a run killed by the tool-failure budget), so four rules are now mandatory. (a) **A guard winds a turn down; it does not kill it.** `agent.abort()` on budget exhaustion killed the in-flight request, so the run ended on a transport string (`Request aborted`) and lost the answer that turn had already produced. Withdraw the tool list and hand the model a runtime notice instead — the tool-*call* budget always did this and the two paths are now one. (b) **An abort message is a symptom; report the cause.** Whatever ended the run must own `errorMessage`, and the user-facing sentence must be written for a person (the budget's `exceededReason` is an instruction addressed to the model). (c) **Status is never content.** `conversationProjection` collapses tool-loop progress; using `content || errorMessage` per entry let a trailing content-less aborted entry overwrite the real reply. The error may stand in as the body only when the turn produced no text at all, and the transcript renders it as a separate note. (d) **A terminal reply is committed content, and a corrective control is steering.** Multiple textual terminal assistants in one run must remain separately visible; non-terminal progress cannot overwrite them. Runtime-authored corrections raised during tools use `steer`, not `followUp`, or they can arrive after completion and manufacture a redundant closing reply. Guarded by `src/lib/server/agent/core/runtimeBudget.test.ts`, the multi-terminal and aborted-turn cases in `src/lib/server/app/conversationProjection.test.ts`, the Runner notice-queue contract in `src/lib/server/agent/core/runner.test.ts`, and the interrupted-turn structural guard in `apps/desktop/src/chat-ui.test.mjs`.
15. **Enabled sandbox must fail closed**: unsupported platforms, missing dependencies, and provider initialization errors must never return the original Bash command or inherit the host environment. The shared Agent/Subagent sandbox boundary either produces a sandboxed command or a structured blocked result. Host execution is legal only after explicit sandbox disable or through the Host Bash approval path. Persisted legacy `warn-disable` values must normalize to `block`; guard provider-unavailable execution and settings round-trip behavior with machine tests.
16. **A resizable column is not the viewport, and a flexible track needs a floor** (one root cause, three shipped symptoms: header title overlapping the action buttons, composer controls spilling past the pane edge, transcript crushed to a sliver when the file panel opened). Two rules: (a) inside any pane whose width is set by a sibling panel — Chat's transcript column, Project Chat, the file panel — never size with `vw`/`vh`. `max-width: 46vw` on the header title and `clamp(20px, 5vw, 56px)` gutters on `.messages`/`.composer-wrap` kept their full-window value after the file panel narrowed the column. Use column-relative `%` (padding and max-width percentages resolve against the containing block) and let flex do the truncating: the title block takes the slack (`flex: 1 1 auto`, `min-width: 0`) while the action row keeps its natural width. (b) a multi-panel grid needs `minmax(floor, preferred)` on the *panels* and `minmax(--chat-min-w, 1fr)` on the content, so the panels give width back first; when the floors stop fitting, drop the SIDEBAR and keep every remaining panel **in flow**. Never resolve a narrow layout by making a panel `position: fixed` over the content: the overlay needs a `z-index`, that `z-index` makes the panel a stacking context, and the panel's own head (`z-index: 31`, deliberately above the `z-index: 30` window drag mask) gets trapped under the mask — its close/refresh buttons go dead with nothing in the console — while the content pane's action row, still laid out full-width underneath, paints straight through the panel. Any absolutely positioned resize handle is driven by the *stored* width, so the stored value must be clamped to the same budget or the handle drifts off the track edge it drags. Only one media tier may own a given `with-files` split; a second full re-declaration in a lower tier fought the first and left an empty panel track. (c) **A flex item's size can silently collapse to zero, and a flex chain breaks at the first item that won't shrink** (issue #28, two symptoms): `container-type: inline-size` applies inline-size *containment*, which sizes the box as if it had no contents — on a content-sized flex item that is 0 width, and with `overflow: hidden` the control's text disappears with nothing in the console (this erased the composer's model name). Only make a query container out of a box whose inline size comes from outside its contents. Conversely, a scrollable modal body needs every ancestor between the `overflow: hidden` dialog and the body to pass the height budget down (`display: flex; flex-direction: column; min-height: 0`); one plain `<form>` wrapper in the chain has an automatic minimum size equal to its content, refuses to shrink, and the body silently never scrolls (Project settings clipped its tail). Guarded by the floor / clamp / gutter / in-flow / single-tier assertions, the no-containment pill assertion, and the project-settings scroll assertions in `apps/desktop/src/chat-ui.test.mjs`.
17. **Theme a third-party widget through its own variables, and verify against its real markup**: `diff2html` (and anything like it) ships a stylesheet with its own `--d2h-*` token set and multiple colour-scheme classes. Overriding a couple of its rules (`.d2h-ins`, `.d2h-del`) recolours only what you named and silently leaves the library's default palette on everything you didn't — hunk row, `d2h-change`, borders, gutter, stat chips — which is what reads as "half-restyled". Remap the library's variables instead, and cover *every* scheme set it defines (`--d2h-*` and `--d2h-dark-*`), since the renderer picks the class (diff2html defaults to `light` regardless of app theme). Equally important: a CSS probe written from hand-authored markup proves nothing about the cascade — it omits the wrapper classes, ancestor selectors and competing rules the library actually emits. Reproduce the vendor's real DOM (or render through the library) before claiming a restyle works. Guarded by the `--d2h-*` remap assertions in `apps/desktop/src/chat-ui.test.mjs`.
18. **Window drag is an ACL problem before it is a CSS problem** (fixed 2+ times, symptom: "the window only drags from its edges" / "the title bar is dead"): both drag paths — Tauri's built-in `data-tauri-drag-region` handler and `WindowDragMask`'s `startDragging()` — invoke `plugin:window|start_dragging`, and `core:window:default` does **not** grant it; the capability must list `core:window:allow-start-dragging` explicitly or every drag is denied at the IPC layer with no console output. Diagnose in that order: check `src-tauri/capabilities/default.json` first (a denied drag that still double-click-maximizes is the tell, since `allow-internal-toggle-maximize` *is* in the default set), and never let a `startDragging()` call swallow its rejection. Only then look at layering: the top 60px is a single `.window-drag-mask` (`z-index: 30`), and a container lifted above it so its buttons stay clickable (`.header-actions`: `flex: 1` + `z-index: 31`) turns its *empty* area into an invisible drag blocker — lift such a container with `pointer-events: none` on itself plus `pointer-events: auto` on its direct children. Note the built-in handler only fires when the element carrying a bare `data-tauri-drag-region` is the direct event target (use `deep` for a subtree), so the attribute on elements *underneath* the mask does nothing. Capability edits need a Rust rebuild, not a WebView reload. Guarded by the top-chrome drag test in `apps/desktop/src/chat-ui.test.mjs`.

19. **Tool syntax in prose is never an answer, on either side of the call** (fixed 2+ times, same root-cause class): weak models on an `@app` turn write the invocation as text. That habit produces two failures with opposite gates, and fixing only one leaves the other shipping. (a) *Before* the call — nothing ran, the reply reads like a success, the user's task was silently dropped. Retry once with an execution-only runtime instruction; the zero-tool gate (`!attemptExecutedTools`) is what makes that retry safe. (b) *After* the call — the work happened and the model closed by writing the call out again (`run tool miniapp__expense-tracker__add with amount is 20 ...`), so the user sees internal syntax and cannot tell whether anything was saved. Here retrying is forbidden: it would replay the side effect. Repair in place instead, by recovering the reply from the last successful Mini App tool result — those results are already written for a human reader, which is what lets the runtime fix this without knowing the app's domain. Detection must differ per side: after a real call, naming a tool can be legitimate, so require invocation-shaped text rather than a bare id mention. Corollary: any runtime instruction about the *shape* of a Mini App reply is shared by every installed app — never name one app's fields (amount/category/date) in it, or it silently misdirects the next app. Guarded by `src/lib/server/miniapps/toolCallIntent.test.ts` and the pseudo-call recovery / domain-agnostic-instruction structural guards in `src/lib/server/agent/core/runner.test.ts`.

20. **A UI reference marker is not a filesystem path, and prose is not a mutation receipt** (second occurrence in the Project `@` feature): the composer may render a readable token such as `@[file](path)`, but the shared Runtime must parse it, validate it against the registered Project root, and hand tools only the canonical path value — never the leading `@`, display label, or raw Markdown. Preserve the display syntax in the transcript and keep the validated mapping transient. Equally, `git diff` written by a model proves nothing: claims that a file was created, edited, or saved require a successful machine-owned `write`/`edit` receipt from that run; a failed tool or empty real diff must remain a failure. Guarded by `src/lib/shared/projectFileReference.test.ts`, `src/lib/server/projects/fileReferences.test.ts`, and `src/lib/server/agent/core/runnerRetryState.test.ts`.

21. **A liveness probe must exercise the real runtime, and a supervisor must never close its own control channel** (root cause of "service 503 behind a green light" + "crashed, had to restart the whole app" + "upgrade left `{workspace}/miniapps` uncreated"): (a) `/api/desktop/handshake` and `/health` are static literals — they answer 200 from a process whose `getRuntime()` throws on every request, and because `getRuntime()` caches nothing on failure the 503 is *permanent*. Any "is it alive" check the supervisor trusts must call a route that actually builds the runtime (`/api/desktop/health?deep=1`), gated behind a handshake capability so an older adopted build answering 404 is not read as unhealthy. (b) Adoption without version identity runs the *old* build's process after an upgrade, so none of the update's migrations or new directories run — compare the running version against the bundled `molibot-runtime.version` and replace on mismatch. (c) A guard *winds a run down; a supervisor must not give up*: returning after N failures drops the `Receiver`, and every later `request_restart`'s `let _ = send()` then fails silently — the "Restart service" button goes dead with nothing in any console. Report `Error` but keep retrying with capped backoff, and park on the channel (never return) after an unrecoverable setup failure. (d) Mini App server modules are `import()`ed into the service process, so one unawaited rejection in a third-party app kills everything — install `uncaughtException`/`unhandledRejection` handlers that write a structured `[mom-t]` crash line + a standalone crash file and release the lease before exiting. (e) Directory bootstrap is data-driven with per-dir try/catch; a test asserts every `*Dir` in `storagePaths` is in the bootstrap list. Guarded by the supervisor Rust suite (`should_replace_adopted`, health classification, backoff cap, `supports_deep_health`), `scripts/runtime/crash-report.test.mjs`, `src/lib/server/infra/db/storage.test.ts`, and `src/lib/server/app/runtimeHealth.test.ts`.

22. **A hand-written packaging manifest drifts from the import graph, and diagnostics must never be a boot dependency** (second occurrence: `bin/molibot-release.sh` first omitted `skills/`, then omitted `scripts/runtime/crash-report.mjs` + `file-logger.mjs`, which made v2.9.0 die at boot with `ERR_MODULE_NOT_FOUND` and restart-loop forever — issue #30). The release script copies runtime modules by **glob** (`scripts/runtime/*.mjs`, minus `*.test.mjs`), never file-by-file: adding a module next to `start-server.mjs` must not require remembering a second edit in a shell script no test exercises. Equally, a module whose only job is observability (crash reports, file logging) is loaded through `loadOptionalRuntimeModule()` and used with `?.` — a missing diagnostic degrades to one stderr line, it does not prevent the service from starting, because the supervisor's restart loop turns any startup-fatal error into a permanently dead app. Guarded by `scripts/runtime/release-bundle.test.mjs`, which resolves every relative `*.mjs` specifier reachable from `scripts/start-server.mjs` and asserts each one is inside the globbed directory.

23. **Liveness is ownership, a lock is not a status, and a guard must never have a silent give-up branch** (root cause of "两个任务一直转圈，而且以后再也不执行了"): (a) **age is not evidence that something is alive.** `recoverStaleRunning` reclaimed only leases older than their timeout, but after a restart *no* `running` lease can still have an in-process owner — a crash inside the timeout window (38s into a 10min budget, in production) left it `running` forever, which pinned the UI *and* made `hasActiveForTask` suppress every future run of that task. Leases carry an `owner_id`; anything owned by another process identity is reclaimed as `interrupted`. (b) **a recovery must not count the thing it is recovering** — `hasActiveForTask` saw the very `retry_wait` lease being taken over and skipped it as `task_already_running`, so pass `excludeLeaseId`; equally a guard keyed on runId (`releasePeriodicRunLock`) rejects the recovery path by construction, because the file holds the *crashed* attempt's runId while the caller carries a fresh one — key on the slot. (c) **every branch that inspects a stuck record must leave it in a terminal state.** `resumeRecoveredLease` returned `false` when the latest lease was a `skipped` bookkeeping row, repairing nothing; a `skipped` row records that a *dispatch* was declined, never the fate of an attempt, so outcome lookups must exclude it and no path may quietly do nothing. (d) **a run *lock* cannot report a result**: a periodic event file's `status` is written back to `pending` on success and left at `running` after a crash, so any UI reading it shows finished and dead tasks identically. Derive the displayed state once, in the shared projection (`resolveDesktopTaskStatus`), from the execution record; "running" means an active lease, not a file field. (e) **automatic replay of a side-effecting task needs a time bound** — catch up only within a window, otherwise report the interruption and wait for the next slot. (f) **writing a log line must never be able to end the process**: a closed supervisor stdout makes `console.log` throw `EPIPE` synchronously, and a fire-and-forget render promise (`void flushQueuedRender()`) turns one network blip into an unhandled rejection — both killed a healthy runtime mid-run. Guarded by `src/lib/server/agent/eventsLeaseStore.test.ts`, `src/lib/server/agent/events.test.ts`, `src/lib/server/app/desktopTasks.test.ts`, `scripts/runtime/crash-report.test.mjs`, and the liveness/single-surface assertions in `apps/desktop/src/chat-ui.test.mjs`.

24. **A design system that exists only in a doc is not a system, and an inline pill's two axes have different budgets** (root cause of "字体不和谐，同一个区域有的大有的小，说不出哪里不好"): (a) **a rule that says "use the tokens" needs the tokens to exist.** DESIGN.md §Typography defines a full type scale and says in as many words to apply it instead of hand-setting sizes — but `styles.css` never declared a single size or line-height variable (it had them for radii, durations, tracking and every colour), so 583 hand-written `font-size: Npx` drifted into 17 sizes and 21 line-heights with no error anywhere. Type is now `--fs-*`/`--lh-*` declared in **pairs**; setting a size without its line-height is how a rank drifts back apart. (b) **an icon size is not a text size.** Phosphor renders glyphs at `font-size`, so 51 icon rules sat inside the text scale and "13px" meant two unrelated things — icons live in `--icon-xs/sm/md/lg`. (c) **one number doing two semantic jobs is the drift.** 12px was both `label` (the model selector) and `meta` (the transcript divider), which is what makes same-rank neighbours look randomly sized; Chat carries exactly three text ranks (body 14/22, label 13/18, meta 11/16) and 12px is gone from it. The tell that a surface never had a scale: the session title was 11px while its own subtitle was 12px. (d) **an element that sets no font-size is not neutral** — with nothing declaring a document size it inherits the UA's 16px, a rank the design does not contain; anchor the surface root on a real rank. (e) **the composer pill is an overlay mirroring the textarea character for character, so no inset may change the advance — but vertical and horizontal are not symmetric.** An inline box's vertical padding never enters the line box (CSS 2.1 §10.6.1), so it is free and needs no cancelling margin; the old rule spent 1px there and 5px horizontally, exactly backwards. Horizontal must be cancelled by an equal negative margin and the real budget is the inter-word space (3.8px at 14px) — 5px was painted *under the following glyph*, which reads as "no right padding" even though it is painting. Any change here is proven by measuring glyph-advance drift in a live render, never by eye. Guarded by the type-scale, no-raw-px, and pill two-axis assertions in `apps/desktop/src/chat-ui.test.mjs`.

25. **The desktop WebView is never same-origin with the service, and there is more than one WebView origin** (fixed 2+ times, symptom: `Cross-site POST form submissions are forbidden` when sending an attachment): any `multipart/form-data` POST from the desktop app (`/api/chat` with files) is a cross-site form submission to SvelteKit's CSRF check. The first fix trusted only the origin in front of it at the time — `tauri://localhost`, the *packaged* custom protocol — leaving `pnpm desktop:dev`'s `http://127.0.0.1:1420` (the Tauri dev server in `apps/desktop/vite.config.ts`) rejected, so the identical failure shipped again in dev. Enumerate every WebView origin in one shared place (`scripts/runtime/csrf-trusted-origins.mjs`: packaged protocol, both host spellings of the dev port, `$TAURI_DEV_HOST`) and let `svelte.config.js` only wire it in; never add origins ad hoc at the call site. Do NOT try to gate the list on `NODE_ENV` — `svelte.config.js` is loaded by the `sveltekit()` plugin factory *before* Vite resolves the mode, so the flag is unreliable there; the loopback/`tauri://` origins are unforgeable by a remote page, so trusting them unconditionally keeps the web deployment's CSRF protection intact. The config only takes effect through a server build, so a dev repro needs a restart, not a WebView reload. Guarded by `scripts/runtime/csrf-trusted-origins.test.mjs` (in `npm run test:service-bootstrap`).

26. **An unrecognized inbound message type must never become the user's text, and a tool must validate before it produces a side effect** (root cause of "配了图片解析模型，AI 却编造了图片内容，还乱调 skill、往群里发了张不相干的图"): (a) **a `switch` over platform message types needs a labelled, logged default.** Feishu `parseFeishuContent` handled `text`/`image`/`audio|media|video`/`file` and let everything else fall through to `String(payload.text ?? message.content)` — so a `post` (rich text = image + text, the normal way a person sends a picture with a question) turned into **the raw event JSON as the user's message**, with the `image_key` nested at `content[0][0]` never downloaded. (b) **a capability gated on a populated array fails silent when the array is empty for the wrong reason.** The whole vision path (`decideVisionRouting` / `decideImageFallbackRouting` in `runnerInputEnricher.ts`) keys off `ctx.message.imageContents.length > 0`; with intake producing `[]`, the runtime *correctly* concluded "no image this turn" and routed to the text model. The configured vision model was never called, `analysisErrors` stayed empty, so even the existing "图片识别不可用" downgrade notice did not fire — nothing anywhere reported a failure. Any "we didn't do X because there was no input" branch needs the *intake* side to warn when it drops input on the floor. (c) **one message carries N attachments, not one.** A single-`fileKey` parse shape cannot represent a multi-image post; model it as `resources[]` from the start. And when a container type mixes element kinds (`post` holds `img`, `media` and `file`), never infer the resource kind from the *message* type — only the element's own tag is evidence. (d) **a side effect before validation is worse than a crash.** `imageGenerate` declared `prompt: Type.String()` but nothing enforced it at runtime; a model with no image reached for the only image-shaped tool, passed an object, `String()` produced the truthy `"[object Object]"`, and the tool generated an unrelated image and **auto-uploaded it into the user's chat**, which the model then described as if it were the user's picture. Validate every param the schema promises *before* the first irreversible step, and make the error tell the model what the tool actually does. Guarded by the post-parsing, JSON-leak, multi-image and unsupported-type cases in `src/lib/server/channels/feishu/message-intake.test.ts` and the non-string-prompt zero-side-effect case in `src/lib/server/agent/imageGenerate/imageGenerateTool.test.ts`. **Second occurrence, Web/desktop intake** (symptom: 上传截图后模型说「没有 OCR 工具」): (e) **`File.type` is not evidence.** `/api/stream` + `/api/chat` classified an upload on MIME prefix alone, but the WebView hands over an empty `type` for drag-and-drop, unknown formats and files synthesized from a path — the screenshot became a plain `file`, `imageContents` stayed `[]`, and (b) fired again verbatim. Classify through the shared `resolveWebInboundFileMeta()` (declared MIME, else extension) and derive `imageContents` from `saved.isImage`, exactly as the channel intakes do, so the two can never disagree. (f) **an attachment path is not evidence of what a tool can do with it.** When no vision route could read the image, the model got only `<channel_attachments>` with a `.png` path and no statement that it was unreadable — so it burned the turn on `skillSearch("OCR")` → `ls` → 「没有 OCR 工具」. Whenever `unreadableImageCount > 0` the Runner now states it in a runtime instruction (domain-agnostic: it may not name a channel, provider or setting, since every surface shares it). Guarded by `src/lib/server/agent/core/runnerInputEnricher.test.ts`, the empty-MIME cases in `src/lib/server/web/attachments.test.ts`, and the unreadable-image instruction guard in `src/lib/server/agent/core/runner.test.ts`.
